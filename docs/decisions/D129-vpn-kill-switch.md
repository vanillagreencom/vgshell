# D129: The VPN kill switch is a pair of nftables tables that systemd re-applies from a user-owned "meant on" file

[← Decision Index](INDEX.md)

**Date**: 2026-11-08

**Status**: Active (Nord peer edits → D130; autoconnect writes → D135)

**Research**: [VGS-2397](https://linear.app/vanillagreen/issue/VGS-2397): owner ask relayed by Jarvis, 2026-11-08; the design and owner sheet attached to the issue; owner approval, Slack message 1794203722.881669, 2026-11-08; the owner's decision on strict block mode and the forward reply rule, made by Jarvis under delegated authority, 2026-11-09; the TCP reset, approved by Jarvis under delegated authority (overseer directive 1794210279-2874999-11855), 2026-11-09; [VGS-2418](https://linear.app/vanillagreen/issue/VGS-2418), the flush, damaged-state and tripped-watcher cases, 2026-11-11; [VGS-2412](https://linear.app/vanillagreen/issue/VGS-2412), the layer-2 paths, with the overseer's answers to design asks 1794412229-2917910-14646 and 1794418739-236677-28375, 2026-11-11.

**Refines**: [D110](D110-tailscale-and-vpn-split.md), for `vgs.vpn`: the plugin gains one system step and writes one state file outside NetworkManager. [D130](D130-nord-location-peer-change.md) permits only the designated Nord profile's public peer change; the no-edit rule still covers every other change.

**Decision**: While a VPN is meant on and its kill switch is on, two nftables tables refuse and count every IPv4 and IPv6 packet that would leave the host by a network device other than the tunnel: the host's own, routed and layer-2 traffic. `inet vgshell_kill_switch` judges the host's own packets and those it routes for its containers and virtual machines, at inet output and forward. `netdev vgshell_kill_switch` holds one egress chain that the kernel hooks on every network device, one created after arm included, so it also judges what a macvtap, macvlan or ipvlan guest, or a guest on a bridge that holds the uplink, switches onto a device at layer 2. Three limits remain. A network card moved into a container's own network namespace is outside the host's hooks. A masqueraded reply to a pod on a netkit device, as Cilium uses, is dropped while the tables are armed. A kernel that cannot hold a wildcard netdev egress hook, such as Linux before 6.16, gets no layer-2 coverage, and the status reads `device-uncovered`. The sync arms, updates and deletes both tables in one nft transaction. Before each arm, it asks the kernel with `nft --check` whether it can hold the netdev table, and arms the inet table alone when it cannot. A two-table arm the kernel refuses after a passing check is a failure, and no inet-only arm follows it. The egress chain drops what the inet table refuses, from sets filled with the same elements. It sees packets after IP fragmentation, so it passes a later fragment toward a WireGuard peer's address, which carries no port. Its DHCP and sign-in passes match only a datagram's first fragment. It passes frames that are not IPv4 or IPv6, ARP included, and frames leaving a bridge, veth, tun or WireGuard device, since those reach another device's egress hook or a host socket the inet table judges. It passes a device by its kind, never by its name, and Tailscale's mark only from a socket on the host itself. The status count is the sum of both tables' counters, and the status reads `state=unavailable reason=device-uncovered` while a network device lacks the egress hook. The tables pass loopback, the tunnel interface, `tailscale0` and packets Tailscale marks (`0x80000/0xff0000`), UDP to the WireGuard peer endpoints, DHCPv4, DHCPv6, IPv6 neighbour discovery and multicast listener reports. In forward, it also passes a tunnel's replies to flows this host masqueraded into the tunnel, which is how Docker containers and NAT virtual machines reach it. In block mode the host refuses its own traffic to its containers and virtual machines, libvirt NAT guests included, so such a guest gets no DHCP or DNS from the host; the local-network allowance passes them. Block stays strict toward the host's own bridges, by the owner's decision of 2026-11-09: a bridge's name does not say whether it holds the uplink, so passing bridges by name could leak. With the local-network allowance on, it also passes private, link-local and multicast addresses, except DNS on ports 53 and 853. While a sign-in page is open, it also passes DNS, HTTP and HTTPS for at most five minutes, through set elements the kernel expires. "Meant on" is `/var/lib/vgshell/vpn/state`, a file the user owns. The shell writes it when the user turns a profile on or off in VGS, and `vgs-kill-switch off` clears it with the shell stopped. A connect whose `nmcli connection up` fails counts as a drop: meant-on stays, and the block holds until VGS's switch or `vgs-kill-switch off` turns it off. One `bin/vgshell-system` row, `vpn-kill-switch`, installs the root script `/usr/local/bin/vgs-kill-switch` and six systemd units. A path unit runs `vgs-kill-switch sync` when the state file or a NetworkManager profile changes. A oneshot runs it at boot before `network-pre.target`. A socket-activated unit answers the armed state, the profile it was armed for and the drop count to any local user. When a flush of the whole ruleset, such as `nft flush ruleset`, removes the tables while the profile cache says the last sync armed it, the status reads `state=off reason=rule-missing`, and the next sync arms it again. A state file the sync cannot read or parse, and a state directory it refuses, fail closed the same way: the sync arms in block from the profile cache, or with no tunnel and no peers and the status reason `state-unusable` when there is no cache, so a damaged file blocks traffic even when the last intent was off, until `vgs-kill-switch off` or VGS's switch rewrites it or its owner repairs a file neither can read. When the path unit hits its trigger limit and fails, its `OnFailure=` starts a timer that starts it again a minute later, so a cause that stays trips it at most once a minute with no setup re-run, and the status reads `reason=watcher-failed` until then. The sync reads the state file with the owner's credentials, reads the profile's interface name and peer endpoints through `nmcli`, and changes only rules and set elements, so the tables and their counters survive each change. It covers WireGuard profiles whose endpoints are IP addresses. Any other profile reads the kill switch as unavailable, with the reason.

**Why**: The block must hold with the shell stopped, across reboot and wake, and while the tunnel is down. Only a kernel rule loaded by system units holds in all of those states, and nftables is the kernel firewall ufw already runs on here. A separate table coexists with ufw without changes to its rules: every base chain on a hook runs, so this table's refusal holds whatever ufw accepts, and ufw never flushes a table it does not own. The user must turn the switch on and off with no password, so "meant on" is a file the user writes and a root unit reads. NetworkManager's dispatcher cannot be the trigger, because turning a VPN off while its tunnel is already down changes no device and runs no hook. `nmcli` cannot write a profile's user data, and changing a profile would break D110's "It edits no profile". The forward reply rule is an addition to the rule set the owner approved: without it, the final refusal drops a tunnel's replies on their way to a masqueraded container or virtual machine, so routing a guest through the VPN stops working while armed. It passes only replies to flows the host's own NAT sent into the tunnel, so it lets no packet out of a non-tunnel interface except a tunnel's reply to a guest whose flow already left through the tunnel. A state file the sync cannot use says nothing about the intent, and the boot kernel holds no table, so failing open would send traffic out the open network at the moment the owner trusts the block. No unit sees a direct `nft` command, so the flush is reported, not repaired: a repair would need the poller this decision rejects. The watcher's recovery is not a watchdog: systemd starts it only when the path unit fails, it runs once and exits, and nothing polls. Refusal, not a silent drop, makes an application fail at once and fall back to IPv4. This matters because px13's Nord profile carries IPv4 only, so IPv6 to the internet is refused even while the tunnel is up. A blocked TCP connection is refused with a reset and fails at once. The inet family has no egress hook, and a netdev chain refuses both conntrack and reject, so the forward reply rule and the resets need the inet table and the layer-2 path needs a second table (measured on Linux 7.3.3 with nft 1.1.7). The egress chain's device wildcard follows new devices in the kernel, with no unit or poller. Anyone can give a device a name, so the egress chain trusts the kernel's device kind. A macvlan or ipvlan guest keeps the mark it set on a packet, so a mark pass open to every packet would let a guest with `CAP_NET_ADMIN` out. The check reads what the kernel can hold, not its version, so a backported or missing feature reads as it is.

**Rejected**: Nord's own app, `nordvpnd`, which Omarchy installs. It is a closed root daemon with its own account sign-in. It covers Nord only and keeps its own interface outside NetworkManager, where `vgs.vpn` cannot show or control it. ufw rules, because ufw holds the user's own rules, each change needs root, and `ufw reset` removes rules it holds. `nftables.service`, because `/etc/nftables.conf` is the system's own ruleset, which every load of that unit replaces: Arch's ships `destroy table inet filter`, and a file that starts with `flush ruleset`, as the nftables package's own `/usr/share/nftables/all-in-one.nft` does, removes every table. A NetworkManager dispatcher hook as the only trigger, because it misses an off press while the tunnel is down. A VGS daemon or poller, because the requirements forbid one and systemd's path and socket units already hold the need. `ReloadPropagatedFrom=nftables.service`, because Arch's `nftables.service` has no `ExecReload=` and refuses a reload, so it would never fire. Refusing the step on a kernel that cannot hold the wildcard egress hook, because that host then gets no kill switch at all, where the inet table alone still holds its own and routed traffic. An egress chain that also judges bridge, veth and tun devices, with a mark bit the inet forward chain sets on a tunnel's replies to masqueraded guests, because Tailscale, NetworkManager and Docker also set bits of that mark, and any program that sets the same bit opens a leak.

**Revisit when**: The owner needs a kill switch for an OpenVPN or other non-WireGuard profile or a WireGuard endpoint that is a host name. Also when NetworkManager gains its own kill switch, ufw or Arch stops using nftables, or the sign-in page needs passage scoped to one browser.
