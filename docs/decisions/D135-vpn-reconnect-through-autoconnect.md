# D135: NetworkManager's autoconnect reconnects a WireGuard profile VGS means on

[← Decision Index](INDEX.md)

**Date**: 2026-11-12

**Status**: Active

**Research**: [VGS-2400](https://linear.app/vanillagreen/issue/VGS-2400): owner request relayed by Jarvis, 2026-11-08; option A, overseer answer 1794550096-443861-29824; the owner's approval of option A, "It should auto reconnect if dropped", Slack message 1794553675.321099, 2026-11-13, and Jarvis's decision under delegated authority to build and ship it, overseer directive 1794553775-679736-13155; nm-settings-nmcli(5), nmcli(1) and NetworkManager.conf(5) of NetworkManager 1.58.1.

**Refines**: [D110](D110-tailscale-and-vpn-split.md) and [D129](D129-vpn-kill-switch.md), for `vgs.vpn`: besides D130's Nord peer change, VGS writes one property of a WireGuard profile, `connection.autoconnect`, when the user connects or turns off that profile in VGS.

**Decision**: VGS keeps a WireGuard profile's `connection.autoconnect` matched to the user's switch in VGS. While the `vpn-kill-switch` step is set up, a connect, from the profile's switch, Connect automatically or Reconnect, runs `nmcli connection modify uuid <uuid> connection.autoconnect yes` once the state file names the profile and any table is armed, then `nmcli connection up`. An off, from the profile's switch or Turn VPN off, runs the same write with `no` whether or not the step is set up, so a yes written earlier never outlives it, then `nmcli connection down`. The down runs also when the last list read shows the profile dropped, since NetworkManager can have brought it back since that read; a down that finds no active connection, nmcli's exit 10 (nmcli(1), EXIT STATUS), completes the off. A failed write fails the change, as a failed `nmcli` run does. NetworkManager's own autoconnect, with `connection.autoconnect-retries` left at its default, brings the profile back after a drop and after a wake. NetworkManager blocks a profile deactivated on request from autoconnecting until it is modified or activated, or until reboot, so an off from a terminal or nm-applet stays off until then while the kill switch holds. A VPN-type profile takes no write, and neither does Remove profile. With the step not set up, a connect does not write yes, as it writes no meant-on. VGS adds no watchdog, poller, retry loop, handshake monitor or wake reaction of its own, and no restart of a WireGuard profile whose peer stops answering.

**Why**: NetworkManager sees each device drop and each sleep and wake as it happens, retries a failed activation, and keeps doing so while the shell is stopped. A reconnect of VGS's own would need a watch on device state or logind, a backoff and a retry loop, which is the watchdog the item rules out, and could not run while the shell is stopped. NetworkManager reconnects a profile by itself only while its `connection.autoconnect` is yes, and implements autoconnect for no VPN-type profile (nm-settings-nmcli(5), `connection.autoconnect`). The write follows the switch, so the profile's autoconnect and D129's meant-on tell a drop from the user's off alike. NetworkManager's connectivity check runs every 300 s by default (NetworkManager.conf(5), `[connectivity] interval`) and only publishes a connectivity state on D-Bus and penalises the default route of a device without global connectivity; it never deactivates or restarts a profile, so a WireGuard profile whose peer stops answering stays activated. Restarting it on that state from VGS would be the watchdog again. One limit stays: `vgs-kill-switch off` with the shell stopped clears meant-on but leaves autoconnect yes, so NetworkManager can bring the profile back, for example at the next wake, with no block.

**Rejected**: A reconnect in `vgs.vpn` driven by NetworkManager's device signal or by the Power plugin's logind watch, because it repeats NetworkManager's retries with a backoff of VGS's own and stops with the shell. A `connection.secondaries` entry on each Wi-Fi and wired profile, because it edits every network profile and activates the VPN only when its base connection activates, never after the tunnel alone drops (nm-settings-nmcli(5), `connection.secondaries`). Setting `connection.autoconnect-retries` to forever, because NetworkManager's default retries and its later retry after a timeout already cover a drop, and a forever value is a second profile edit with no failure it fixes.

**Revisit when**: The owner's suspend and wake on px13 shows NetworkManager does not bring the profile back; a wake reaction then reads the wake through a core-lent fact, never a second logind watch. Also when NetworkManager implements autoconnect for VPN-type profiles and a user needs one to reconnect, or when NetworkManager offers an action on a dead WireGuard peer.
