# Runtime: devices

Covers: scripts/smoke/fixtures/devices/world.py, scripts/smoke/fixtures/devices/pipewire/, scripts/smoke/fixtures/plugins/acme.devices/, shell/plugins/vgs.sound/Audio.qml, shell/plugins/vgs.sound/SoundControls.qml

The Quickshell 0.3.1 facts a plugin that reads Bluetooth, the network or PipeWire rests on, each with the source that establishes it, under `src/` of [Quickshell v0.3.1](https://github.com/quickshell-mirror/quickshell/tree/v0.3.1). The smoke's fakes for them are in [validation-smoke-devices.md](validation-smoke-devices.md). [runtime-qml.md](runtime-qml.md) holds the other QML facts.

- `Bluetooth` and `Networking` look for their service once, when the singleton is first created, which is when a plugin first reads it. `Bluez::init` calls `DBusObjectManager::setInterface("org.bluez", "/")` on the system bus, which gives up when the name has no owner; the NetworkManager backend constructs its proxy once and runs `init` only when `isValid()` (`bluetooth/bluez.cpp`, `dbus/objectmanager.cpp`, `network/nm/backend.cpp`). Neither watches for the service to appear later, so a service started after that first read is never seen by that shell.
- Every D-Bus property Quickshell binds with `QS_DBUS_PROPERTY_BINDING` is required unless the binding passes `false`: a `GetAll` answer without it logs `<name> missing from property set` from `quickshell.dbus.properties` and leaves the value unset (`dbus/properties.hpp`, `dbus/properties.cpp`). `BluetoothAdapter.state` reads `org.bluez.Adapter1.PowerState`, and `BluetoothDevice.bonded` reads `Device1.Bonded` (`bluetooth/adapter.hpp`, `bluetooth/device.hpp`). NetworkManager's devices are listed with `GetAllDevices`, and a device reads `Device.HwAddress`, `Autoconnect` and `InterfaceFlags`, a Wi-Fi device `LastScan` and `ActiveAccessPoint`, and the manager `ConnectivityCheckAvailable` and `ConnectivityCheckEnabled` (`network/nm/*.hpp`, `network/nm/backend.cpp`). python-dbusmock 0.38.1's `bluez5` and `networkmanager` templates lack each of these; `scripts/smoke/fixtures/devices/world.py` adds them.
- A `WifiDevice`'s `networks` lists a network only while the device scans, `scannerEnabled` true, while it is connected to that network, or while it holds settings for it (`registerNetwork` in `network/nm/wireless.cpp`). Setting `scannerEnabled` calls `RequestScan`, again at most every scan interval.
- `Pipewire.nodes` types a node by its exact `media.class`: `Audio/Sink`, `Audio/Source`, `Audio/Duplex` and the two audio streams carry `audio`; `Audio/Source/Virtual`, the class PipeWire documents for a virtual source, is no audio node (`PwNode::initProps` in `services/pipewire/node.cpp`). A node's `name`, `isSink`, `isStream` and `audio` are set when it appears, with no `PwObjectTracker`.
- `Pipewire` connects once, when the singleton is first created, to the socket in `PIPEWIRE_RUNTIME_DIR`, else `XDG_RUNTIME_DIR`. A failed first connection logs a critical, an `ERROR` line in the instance log, and is not tried again unless `QS_PIPEWIRE_IMMEDIATE_RECONNECT` is 1; only a connection lost later watches the runtime dir for a new socket (`PwConnection` in `services/pipewire/connection.cpp`, `PwCore::start` in `services/pipewire/core.cpp`). The variable does nothing else: with it, a failed first connection starts the same watch, and its later tries log at info level. `bin/vgsh run` sets it for the shell, so PipeWire that starts after the shell is connected as one that restarts is; `scripts/test-vgsh.sh` pins the variable, and `scripts/smoke/rows/sound.sh` reads a shell started with PipeWire stopped reach it once PipeWire starts, beside a runner copy without the variable that never does.
- `PwNodePeakMonitor` reads a node through a capture stream of its own, which PipeWire brings up FL FR whatever the node's channels. For a node with no device behind it, such as a virtual source or the smoke's `audiotestsrc`, it maps each stream channel to one of the node's and logs a critical, an `ERROR` line in the instance log, on every buffer when one is missing, as a mono node's are (`PwPeakStream::handleProcess` in `services/pipewire/peak.cpp`). The smoke's test source is stereo for that reason. Read in the nested smoke on host cachy on 2026-10-02.
- `Pipewire.ready` turns false when a connection is lost, as when PipeWire stops: `PwConnection::onFatalError` resets the registry, and its nodes go. The new socket a restarted PipeWire makes in the runtime dir brings it back, through the runtime dir watch a lost connection starts, as the fact on its first connection above states. `scripts/smoke/rows/sound.sh` reads both.
- A PipeWire client reads its own `client.conf` from `PIPEWIRE_CONFIG_DIR` when that is set, so `pw-dump` fails with `can't load config client.conf` under a directory that holds only `pipewire.conf`; the smoke sets `PIPEWIRE_CONFIG_DIR` on its daemon alone. A daemon that loads no `libpipewire-module-access` grants no client its permissions, and no client, WirePlumber included, gets past its first round trip. Both were read with PipeWire 1.6.9 and WirePlumber 0.5.17 in a private runtime dir on host cachy on 2026-09-30.
