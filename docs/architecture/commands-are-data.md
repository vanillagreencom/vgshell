# Commands are data, and they run where the user sees them

Read before touching the `tui` capability, a manifest's `tui` or `systemSteps` key, `bin/vgshell-tui`, `shell/Core/PackageManagers.js`, `vgshell pkg`, `bin/vgshell-system`, `vgshell sudo grant`, a udev rule VGS ships, the Dev Tools catalog, the requirement notice's install, or any place a plugin's or a user's text could become a command or a flow could ask the user a question or a password.

## The approach

Text a plugin, a catalog or a user supplies never becomes shell code, and anything that asks the user or needs root runs in a terminal the user sees. A plugin declares its scripts as data in its manifest's `tui` key and opens them by name through `shell.tui`; the Dev Tools catalog stores argument arrays. `shell/Core/PluginLogic.js` makes every decision about what a plugin may open. One launcher, `bin/vgshell-tui`, runs the command as an argv list in a floating terminal that outlives the shell, or, for Connect in terminal's ssh session, in a tiled window of the user's terminal, and the core learns that a run ended by blocking on the run's own lock ([D043](../decisions/D043-tui-run-ends-by-lock-release.md)). Every install, remove, upgrade and update check reads the one table in `shell/Core/PackageManagers.js`, and a package change runs only through `vgshell pkg run` in that terminal. Every privileged setup or repeatable system operation is one row of the closed table in `bin/vgshell-system`: a plugin names a row in its manifest's `systemSteps` and never supplies a root command. The shell process never elevates. The choices are [D033](../decisions/D033-floating-tuis-are-core.md), [D034](../decisions/D034-one-package-manager-table.md), [D081](../decisions/D081-system-steps-closed-core-table.md) and [D103](../decisions/D103-passwordless-sudo-timed-or-indefinite.md).

## Why

A string that reaches a shell becomes code, and a plugin's or a catalog's text would then run outside the shell with the user's privileges. Reading the same data from a judged manifest keeps a launcher able to list other plugins' tools without naming those plugins ([D005](../decisions/D005-kinds-are-surfaces-no-dependencies.md)). A password typed into the shell process would be a secret in a QML field, a log or IPC, and a shell process that elevated would hold root with no one watching; a terminal the user sees is the one place a prompt can be answered. Separate per-flow package lists disagree on argv, and a query whose exit status the table does not list cannot be read. A plugin must never hold root commands the core did not judge, and a user-writable record could steer `undo` into disabling a unit VGS never touched.

## Rules

### Commands as data

- Do declare each script under the manifest's `tui` key, in the plugin's `tui/` directory, with capability `tui`; `PluginLogic.tuiError` refuses the rest, pinned by `scripts/test-plugin-logic.js`.
- Do ship each script as a regular file with its owner's execute bit, reached through no symbolic link; `bin/vgshell-scan` follows links when it publishes a snapshot, so a link would publish whatever it points at. `bin/lib/check-manifests.js` refuses one.
- Never open a script the manifest does not declare, from anything but the published snapshot ([D014](../decisions/D014-source-revisions-are-published-snapshots.md)), or while the plugin is disabled. `scripts/test-tui-logic.js` and `scripts/smoke/rows/tui.sh` pin it.
- Do key a core TUI `core/<name>` whatever its arguments, so one plugin update runs at a time, and answer a busy key by revealing the live window, never by a second terminal. `scripts/test-tui-logic.js` pins both.
- Do key a plugin's own script `<plugin id>/<name>` whatever its arguments, and answer a manager request for a busy key whose live run took other arguments, such as another row's Remove, with `reason=busy-other` while revealing that window, never `ok`. Answer a request for the core editor, `core/edit` or a file action's `<plugin id>/edit`, the same way while it holds another file, so a link to one file never answers `ok` with another file's editor; the editor's answer for a file comes once `gio info` read the file, to the `done` of `shell.tui.edit`. A requirement notice that holds a request for a script refuses one for that script with other arguments the same way. `scripts/test-tui-logic.js` pins both.
- Do hand a script only arguments the core read from what the plugin published: a row action's row id, and a stored key's source action its account and the label of the item published for it at the press, never text the page sends. `PluginLogic.statusActionRequest` reads both, and `scripts/test-plugin-logic.js` pins them.
- Never let a `missing` launcher start a process; answer `launcher-missing`. `scripts/smoke/rows/tui.sh` pins it. The ssh session of `shell.tui.ssh` is the exception: a missing terminal launcher does not prevent attached-client reuse, so `PluginLogic.tuiSsh` refuses only bad arguments and starts the launcher in every launcher state. `scripts/test-tui-logic.js` and `scripts/smoke/rows/tailscale.sh` pin it.
- Never hand a TUI command or a package step to a shell string; each is argv. `scripts/test-vgshell-tui.sh` and `scripts/test-vgshell-pkg-run.sh` pin it.

### Dev Tools catalog

- Never write a shell string in the catalog; every command there is argv. `scripts/check-devtools-catalog.js` refuses one.
- Never use `sh -c`, `eval`, `python -c`, `node -e`, `env -S` or a versioned interpreter form, and never `@latest`; a bare name is the current version. `scripts/check-devtools-catalog.js` pins each.
- Do bind a catalog database port to `127.0.0.1`, use every `brand` key in `Appearance.js`, and name only `PackageManagers.js` ids in a package map. `scripts/check-devtools-catalog.js` pins each.

### Floating TUIs

- Do centre every size class and derive its height from its share of the output's logical height, capped by the output less `Theme.bar.height` and two `size.window.gutter` margins. Each class keeps only the row floor its content needs, derived beside `HyprlandLayer.TUI_WINDOWS`; the logo, package table and transcript can scroll. Each floor includes `TUI_PADDING` at the layer's estimated terminal cell size; a floor that cannot fit inside the gutters takes them before it loses cells, and always keeps the bar and outside border. `HyprlandLayer.tuiLength` owns the bounds, and `scripts/test-hyprland-layer.js` pins px13's 1440×900 logical output.
- Do show commands through `bin/lib/tui.sh`'s `vgs_tui_commands`, after a plain sentence that says what the step changes. `scripts/test-tui.sh` pins the block.
- Do launch every flow that asks the user anything, a password or a y/N, through `bin/vgshell-tui`, and hand `present` everything it needs in argv. `scripts/test-vgshell-tui.sh` pins it.
- Do fork the terminal with `setsid -f`; Quickshell kills its children when the shell stops, and a restart during an install must not kill the install. `scripts/test-vgshell-tui.sh` pins it.
- Do run a plugin's script from a private copy of its whole published snapshot; a restart removes old snapshots while a script may still read its plugin's files. `scripts/test-vgshell-tui.sh` pins it.
- Do strip `VGSHELL_RUNNER_PID` from the terminal's environment; a single-instance terminal hands it to later windows, and `vgshell pkg run` refuses it. `scripts/test-vgshell-tui.sh` pins it.
- Never source `gum.env`; parse it, and one bad line exports nothing. Put the Done or Failed prompt on `/dev/tty`, not stdout. `scripts/test-vgshell-tui.sh` pins both.
- Do let the presenter, the only process that knows when the command ended, write the run's record whole under a hidden name and rename it; never rewrite one, a new state is a new file, and never let the command inherit the key lock or the run lock. `scripts/test-vgshell-tui.sh` pins each.
- Do treat the wait on the run lock as the completion guarantee; never start two waits for one run, and never poll a process. `scripts/qml-tests/tst_tui_records.qml` and `scripts/test-tui-logic.js` pin each.
- Do keep a key's last ended record across a shell restart. `scripts/test-vgshell-tui.sh` pins it.
- Do hold one sudo session per script; a nested session joins a live owner. `scripts/test-tui.sh` pins it.
- Do pick a size class from `HyprlandLayer.TUI_WINDOWS` in `shell/Core/HyprlandLayer.js`, never a geometry. `PluginLogic.tuiError` refuses another, pinned by `scripts/test-tui-logic.js`.
- Never choose the user's terminal; it floats only when its desktop entry carries `X-TerminalArgAppId`. Gap: no check pins it.
- Do open an ssh session through `shell.tui.ssh` alone: the core judges the device name and host (`PluginLogic.tuiSsh`) and builds every argv. With an attached `tailnet` client, `bin/vgshell-tui ssh` creates and selects the device window and reports the client's PID without opening a terminal; the core focuses its window through `Compositor`. Otherwise bash opens the user's terminal with no app-id, so the window tiles, and refuses a terminal that fails at its start. Keep no key, record or wait for this user-owned session. Only tmux queries and window creation/selection may run under the shell; ssh and persistent attached clients stay in the terminal. Keep the name and host as argv data, and a failed terminal-side ssh or tmux step on screen until a key. Set status-right only on a `tailnet` session VGS creates, never globally or on another session. `scripts/test-vgshell-tui.sh` pins the argv and tmux plan with stubs, and `scripts/test-tui-logic.js` the judge. The launcher reply is in the [TUI API](../../.agents/skills/vgs-plugin/references/api.md).

### Packages

- Never name an elevation command in a step or a picker, never refresh a pacman-family database without upgrading, and never pass `--noconfirm` or `-y`. `scripts/test-vgshell-pkg-table.js` pins each.
- Do refuse `vgshell pkg run` in a process the shell started and without a terminal. The shell removes `VGSHELL_RUNNER_PID` only from the programs it opens for the user, so a plugin process never elevates and a user's own terminal is not refused. `scripts/test-vgshell-pkg-run.sh` pins it.
- Do run steps and queries from `$HOME`, so a project's `mise.toml` cannot change what a check counted. `scripts/test-vgshell-pkg-run.sh` and `scripts/test-vgshell-pkg-cli.js` pin it.
- Never add a query whose exit statuses the table does not list, and give every parser a canned output under `scripts/fixtures/pkg/`, so a parser given a changed format fails rather than miscounts. `scripts/test-vgshell-pkg-table.js` pins both.
- Do run one check at a time under the lock, and end a query past its timeout with its process group. `scripts/test-vgshell-pkg-cli.js` pins both.
- Do give nix no steps and no check; a NixOS system changes through its configuration.
- Do take a package from a repository pacman.conf does not list only through the `verified-file` row, whose closed list names each repository, its key under `config/keys/`, the key's fingerprint and the packages taken from it; never add such a repository to pacman.conf or its key to the system keyring, which would trust every package the key signs. As the user, `bin/lib/pkg-file.js` refuses a `LocalFileSigLevel`, or the `SigLevel` it inherits when unset, that requires a signature, a version older than the installed one, a sha256 the database does not name, a signature whose `VALIDSIG` does not name the pinned fingerprint and a `.PKGINFO` naming another package or version, before any root step. Root then copies the file and its `.sig` into separate folders, checks the copy again and runs `pacman -U --needed` on a file with no `.sig` beside it, so pacman never asks to trust the key, then removes that package's older cached files and signatures. Updates runs the row's upgrade through the same route, in Update all only while one of its packages is installed. Each refusal says in plain words that nothing was installed. The pinned signature is the origin evidence, so the row takes no package review. `scripts/test-vgshell-pkg-table.js` pins the foreign signature, the downgrade, the update check, the separate folders, the cache prune and the shipped key's fingerprint; `scripts/test-updates-pipeline.sh` pins the Updates run.
- Do take a package that apt's or dnf's repositories lack, and whose upstream publishes it as a release asset, only through the `deb-file` or `rpm-file` row, whose closed list pins one release of each package: its download address, version and each architecture's file and SHA-256. As the user, `bin/lib/pkg-file.js` refuses an architecture the release lacks, an installed version newer than the pin, a SHA-256 other than the pinned one and a package file whose name, version or architecture differ from the pin, before any root step. Root then copies the file into a folder only root writes and the manager installs that copy, resolving its dependencies from the system's repositories. Never add a repository for it. The user's check is the trust point, as for the engine archive: root reads only the copy the check passed. `scripts/test-vgshell-pkg-table.js` pins the digest, the identity, the downgrade and the plan.

### Package review

- Do run paru's agent review in its file-manager review step, over the clones paru then builds ([D133](../decisions/D133-paru-file-manager-review.md)). `PackageManagers.reviewedBuild` owns `--review --nosudoloop --fm` and the saved decline's `--skipreview`. Refuse foreign leading file-manager arguments by naming paru's FileManagerFlags setting. After a successful paru build, run `--gendb` once; report a built devel base it leaves untracked as a result line, never a failed install. Repository packages and removals take no agent review; yay keeps its own review menus. `scripts/fixtures/pkg-review/runtime-test.js` pins the common route for Updates, picker, notices, terminal calls and retries.
- Do copy only a base's tracked Git HEAD files and paru's supplied diff into a private review folder. Copy a file only when it equals the clone's checked-out file, which makepkg sources; any difference makes the review unavailable. List tracked symbolic links without following them. Keep a pristine snapshot outside every agent write root and give each agent attempt a fresh copy, so an unsuccessful agent cannot change a fallback agent's input. Never copy build output or review inside a build clone. The helper bootstrap keeps its own clone fetch and reviews that same clone through the common review owner. `scripts/fixtures/pkg-review/copy-test.js` and `scripts/fixtures/pkg-review/runtime-test.js` pin these boundaries.
- Do judge publisher ownership through `PackageReview.publisher` over the shipped Arch recipes. Exempt a base only when every package it builds is VGS-published. Unread publisher declarations grant no exemption. Skip paru's review questions for VGS-only targets only when its read-only full build order contains no other AUR base. A new AUR dependency keeps the review. `scripts/fixtures/pkg-review/runtime-test.js` pins this rule.
- Do read each complete PKGBUILD, install script and local source file on every review. A diff only points at changes. `PackageReview.parseVerdict` owns the verdict and `installScriptChange` keeps the deterministic install-script check. `bin/lib/review/third-party.md` owns the agent's signals; `scripts/fixtures/pkg-review/recipes-test.js` keeps their recipe evidence and deterministic checks.
- Never put a build clone, stored verdict or outcome beneath an agent-writable root. The review owner keeps verdicts by base and tree, and the outcome, under `$XDG_RUNTIME_DIR/vgshell/updates/`, outside the evidence folder, `/tmp`, `$TMPDIR` and Claude's stable start folder. Shipped agent commands keep their confined flags. Saved commands run as written with the same start-folder choice; an unsandboxed saved command has the user's write access. `scripts/fixtures/pkg-review/runtime-test.js` pins folder placement and `scripts/fixtures/pkg-review/logic-test.js` pins shipped launch arguments.
- Do offer the other available agent first when an agent ends without a verdict, with its name, the verdict's problem and its sanitized last line, or when the chosen agent is not installed. A signal during the agent cancels the AUR step. Install without review requires consent. Skip AUR packages and Stop skip only the AUR step, with status 0, as a Skip of every named package does; the helper bootstrap reports its review the same way, and self repair stops when paru is still missing. Pass upstream lines through `PackageReview.failureLines` before storing or showing them in a result. `scripts/fixtures/pkg-review/runtime-test.js` pins the choices, the cancel and masking.
- Do skip a flagged package and every pending dependent when the owner chooses Skip. Retry paru once with those names ignored; retain its review step and reuse accepted verdicts only for unchanged base/tree pairs. Report each flagged package and its dependents on a result line of its own, and the review's outcome only from the final paru call. Never consume a receipt or compare a later package plan with an earlier review. `scripts/fixtures/pkg-review/runtime-test.js` pins the retry and `scripts/test-updates-pipeline.sh` the Updates results. Paru's Proceed to review and Accept changes remain its own questions; paru installs built packages without a separate pacman confirmation unless there is a conflict.
- Never review inside a live outer credential session. Bootstrap a missing helper separately and end Updates' session before its AUR builds. Before an agent starts, end each saved authorization an earlier paru step leaves for this user's later processes, through `PackageManagers.CREDENTIAL_DROPS` for each elevator on PATH: sudo's terminal timestamp and run0's polkit session authorization. A process outside any logind session cannot revoke, yet polkitd maps it to the user's display session, so the review goes on only when polkit answers that it holds no run0 authorization. doas needs none, since its persist record belongs to the parent process that ran it. `scripts/fixtures/pkg-review/world.js` keeps every fixture world on stand-ins for these commands. Keep generated hook configuration under the run's lifetime owner; its hook policy belongs to the reboot-notice flow. Build cleanup never clears a live outer owner's credentials. `scripts/test-updates-pipeline.sh` pins the session boundary.
- Do preserve PackageManagers as the mutation argv authority. Named skips filter targets; upgrade skips use its ignore option. An unknown custom AUR command keeps explicit unavailable-review consent and its original argv; a No is a declined step. Recheck installer package prerequisites after a successful partial/skipped request before publishing the staged tree.

### Package build failures

- Do judge a failed AUR build only through `PackageReview.classifyInstallFailure`, over the complete interval `bin/lib/tui.sh` cut from the build's terminal transcript while the build kept the terminal on stdin, stdout and stderr. Only one makepkg `check()` failure of one requested base, from a supported makepkg and paru in English, qualifies. Incomplete, unsupported, localized, mixed or signalled evidence keeps the ordinary failure and its status; evidence the classifier could not read prints its keyed cause, and no copy of the classifier lives in Updates, the presenter or a notice. `scripts/fixtures/pkg-review/failure-test.js` pins it on the transcripts under `scripts/fixtures/pkg/check-failure/`.
- Do offer one retry without tests only on the user's choice, Stop selected, built from PackageManagers' `retryPlan` or `bootstrapBuild` for the one failed target, and run it as the original build ran: the helper asks sudo for itself under the build guard, never inside a live outer credential session. Never retry by itself, persist a flag or skip a source integrity check. A prepared Updates step keeps Updates' own failure report. `scripts/fixtures/pkg-review/runtime-test.js` pins each.
- Do consume a retry before it runs. Only a requirement notice's run that stopped holds its retry, in the package owner's private work folder. A newer run of the key or the end of its record retires it, and `vgshell pkg retry` claims it once, then takes the current helper and configuration through the same file-manager review. `scripts/fixtures/pkg-review/runtime-test.js` pins each.
- Do carry a package run's outcome only through the presenter's private outcome channel: the owner the presenter runs directly writes it once, and the presenter alone judges it with `PackageReview.packageOutcome` and puts it in the ended record. `scripts/test-vgshell-tui.sh` pins it.
- Do carry a failed install's or update's last lines in its outcome only as `PackageReview.failureLines` keeps them from the failed step's cut: the step's own output, never its command block or a prompt's answer, with a mirror's or a proxy's user and password and a token shape masked. The judge refuses a line it would change. `scripts/fixtures/pkg-review/failure-test.js` pins both.
- Do read an ended record's outcome through the same judge in `PluginLogic.tuiRecord` and hand it to the run's `done` as `package`; an outcome the judge refuses is logged and leaves `package` null, never the run's completion. `scripts/test-tui-logic.js` and `scripts/qml-tests/tst_tui_records.qml` pin it.

### System steps

- Never add a root action outside the table in `bin/vgshell-system`; a manifest's `systemSteps` names table rows only, and dictation setup offers the table's `voxtype-engine` step for its engine switch. `scripts/test-vgshell-system.sh` and `scripts/test-plugin-logic.js` pin it.
- Do write the record, root-owned under `/var/lib/vgshell/system/`, before the commands, so a partial failure is on record, and undo only the recorded change, for the caller's uid, in the boot that made it. `scripts/test-vgshell-system.sh` pins both.
- Do keep a profile-dependent setup reading pending after a profile change until a requested fresh system probe completes. An unchanged value still acknowledges that read; failed start, unreadable output and expiry replace prior readings with unknown. `SystemSteps` owns that probe and its queued rerun, and status action completion belongs to the requesting instance while the core always probes after a system run.
- Do probe real access, never a file's presence; a probe that cannot answer reads `unknown`, never `ready`. `scripts/test-vgshell-system.sh` pins the `unknown` state.
- Never overwrite a destination VGS did not write; refuse a symlink destination and a foreign file as `foreign`. `scripts/test-vgshell-system.sh` pins it.
- Do grant a device by `uaccess` alone, in a rule that sorts before `73-seat-late.rules`, which applies the tag; a `GROUP` or `MODE` grant reaches SSH and other-seat sessions. `scripts/test-vgshell-system.sh` pins the shipped rule.
- Do set a DNS provider through the Wi-Fi and Ethernet profiles' own `ipv4.dns` and `ipv6.dns`, each server with its TLS name, and a VGS drop-in under `/etc/systemd/resolved.conf.d/` that holds the fallback and DNS-over-TLS lines alone. Never write a global `DNS=` line, a NetworkManager `[global-dns]` file or `/etc/systemd/resolved.conf`, and never touch a `vpn`, `wireguard`, `tun` or other profile, its DNS priority or `tailscale0`. A port profile has no IP settings unless it is a VRF's port, so the steps skip every port but a VRF's, which takes the provider like any other profile. resolved sends every unmatched name to a global server beside the VPN, so the global line would leak public lookups past a full-tunnel VPN. The steps rely on NetworkManager's own DNS priority, 50 for a VPN against 100 for other profiles, to keep the VPN's `~.` route ahead of the Wi-Fi and Ethernet links, and set no `dns-priority` of their own. `scripts/test-vgshell-system.sh` pins the drop-in, the untouched VPN profiles and the unchanged priorities; the routing itself is NetworkManager's and resolved's, which no row runs. Gap: a WireGuard full tunnel through NetworkManager's automatic policy routing never claims `~.`, since NetworkManager finds a default route only in the main table, so public names keep going to the Wi-Fi or Ethernet link's servers whatever the provider, unless that profile carries `~.` in its DNS search.
- Do record each profile's two `ignore-auto-dns` values and two server lists before the first DNS change, keep them across a change of provider, and let undo of any DNS step restore them and remove the drop-in. A profile changed after apply keeps its new values. A change of provider that stops part way records the servers the earlier provider set on each profile it has not reached, so applying it again and undo still read them as VGS's. A refused `nmcli device reapply` only warns, since the profile holds the choice and the device takes it when it next connects. A profile that carries servers no VGS record names reads `needed` with reason `foreign`, a reading and never a refusal. NetworkManager has no per-profile DNS default a VGS process does not run, so a choice covers the networks known when it is applied; a network joined later reads reason `partial` until the choice is applied again, and the apply text says so. `scripts/test-vgshell-system.sh` pins each.
- Never start greetd from inside a session, enable it only, and refuse the greeter step unless the install tree is root's and writable by no one else, since the greeter account runs where every password is typed ([D101](../decisions/D101-greeter-host-and-greeter-system-step.md)). `scripts/test-vgshell-system.sh` pins both.
- Do resolve every command of the sudo grant's root half in the system directories alone, drop the sudo credential before and after each verb that reaches it, and run the root half under `bash -p` with `PATH`, `LC_ALL` and `SUDO_UID` alone. `scripts/test-vgshell-sudo-grant.sh` pins each under `unshare -r`.
- Do publish a timed grant by rename only after its expiry timer is armed and the boot cleanup is in place, with a `NOTAFTER` rule sudo ends itself. `scripts/test-vgshell-sudo-grant.sh` pins it.
- Do write nothing and run no sudo on NixOS; print the configuration snippet instead, for the grant the `security.sudo.extraRules` snippet. `scripts/test-vgshell-sudo-grant.sh` and `scripts/test-vgshell-system.sh` pin the `nixos` state.
- Do keep the VPN kill switch in the kernel tables `inet vgshell_kill_switch` and `netdev vgshell_kill_switch`, which the `vpn-kill-switch` step's systemd units arm from the user's `/var/lib/vgshell/vpn/state`, read with that user's credentials. Every interface name, address, port and number reaches `nft` only after its validator, and no VGS daemon or poller holds or re-applies the rule ([D129](../decisions/D129-vpn-kill-switch.md)). `scripts/test-vpn-kill-switch.sh` pins the rule, the off, the clear and the status read in network namespaces, and `scripts/test-vgshell-system.sh` pins the step.
- Never let a step reach the host's devices, units or sudo in the sandbox. `scripts/smoke/rows/system-steps.sh` and `scripts/smoke/rows/auth-sentinel.sh` pin it.

### Consent

- Do start every install, root change and plugin or theme change from the user's own press, and show every root command before it runs, then run only the plan shown. `scripts/test-vgshell-system.sh` and `scripts/test-vgshell-sudo-grant.sh` pin it.
- Do let the package manager ask for root in the floating terminal, never in the shell: the requirement notice's Install opens the core TUI `core/requirements-install`, one manager per press.
- Do keep a requirement notice for an exact-run classified package-test failure only while its latest ended key/run, manager and target still match the requirements owed after rescan, version settlement and manager detection. The notice consumes the judged outcome, never terminal text or a second classifier. An available owner-held retry passes only originRun through the closed core retry TUI; the package owner reconstructs and claims its plan. Consumed authority offers an ordinary tests-enabled install or update. A retry success settles only the requirements found after it, never the original batch from exit zero. `scripts/test-notice-logic.js` and `scripts/smoke/rows/notices.sh` pin it.
- Do close every other failed plugin requirement notice, as Not now does, and refuse the plugin's suggestions until its next install attempt, so the notice never comes back by itself, and show the failure on the plugin's Setup step instead, as the run's ended record carried it: what failed, its last lines and Try again, which runs the same step with no notice. The attempt is kept from the press, so the failure stays across a shell restart, one during the run included, until the next install attempt for that plugin, and a run that ends with code 0 clears it. One install runs at a time, whether Install or Try again started it. The core's own notice stays open and says its run failed. `scripts/smoke/rows/notices.sh` pins it, with `scripts/smoke/rows/notices-control.sh` as its control, and `scripts/test-notice-logic.js` pins what is kept. `scripts/smoke/rows/notices.sh` pins the Install run, and `scripts/test-vgshell-pkg-run.sh` refuses `vgshell pkg run` in a shell process. `PluginLogic.noticeRequest` decides which requirements a notice lists, `PluginLogic.noticeHeld` those a script's notice lists, and `PluginLogic.noticeAdmit` decides when an offer a plugin raises with no press rests; an offer a press raises never rests.
- Do keep the question a command asks on its terminal: a core TUI that adds, updates or removes a plugin or a theme runs without `--yes`, and the prompted theme add asks before it applies the new theme ([D007](../decisions/D007-install-runs-no-plugin-code.md)).
- Do open the requirement notice instead of a plugin's script while a command the script needs is missing. `scripts/test-tui-logic.js` pins it.

## Revisit when

`xdg-terminal-exec` drops `--app-id`, gum changes its environment names, a TUI needs a geometry no size class covers, a supported package manager cannot be expressed as argv steps, the shell must change a package with no terminal open, a step needs a privilege a sudo command cannot give, a distribution ships these grants itself, a Flatpak presence and launch model exists for the catalog, or NetworkManager gains a per-profile DNS default or reads a WireGuard policy-routed default route for DNS.

## Not governed

Which commands a plugin needs and the requirement notice's queue, which are `PluginLogic.noticeRequest` and `PluginLogic.noticeAdmit`; the functions of the presentation library, which `bin/lib/tui.sh` lists in its header; the one elevation a shell process performs, the Chromium policy writer, which is [D029](../decisions/D029-chromium-policy-writer.md); the greeter host's own rules, which are [D101](../decisions/D101-greeter-host-and-greeter-system-step.md) and the `vgs.greeter` README.
