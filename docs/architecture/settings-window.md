# The Settings window

Covers: shell/plugins/vgs.settings/**, scripts/smoke/rows/manager.sh, scripts/smoke/rows/settings.sh, scripts/smoke/rows/windows.sh, scripts/smoke/rows/scratchpads.sh

The Settings window is the plugin manager's user interface: the `vgs.settings` plugin, which reaches the manager through the `manager` capability ([manager.md](manager.md)).

## The window

- **Surface.** A `window` summon: an application window, which the window host builds as a Hyprland window titled Settings when summoned and destroys on hide ([surfaces.md](surfaces.md)). Hyprland draws its border, floats it and centres it on the work area through the layer's `vgs:window` rule, gives it the keyboard while it is focused and moves it, tiles it and closes it on the user's keys; a close through Hyprland is a hide. It asks to be `min(size.window.width, screen width − 2 × size.window.gutter)` wide and `size.window.heightShare` of the screen's height tall, read from its `screens` capability, and its pages fill whatever size it has after. It draws no frame of its own. The gear, the `toggle` shortcut, `SUPER+M` in the manifest, and the IPC open it on the focused monitor; a click on the gear focuses the gear's monitor first.
- **Pages.** The list page holds a search field and one row per manager row; the plugin page holds a back button and the plugin's name as a `TitleButton` whose `Menu` lists every plugin, the current one checked, and jumps to another's page. Its body is two pages under one `TabPages` strip ([components-layout.md](components-layout.md)), with the plugin's errors and the last refusal above the strip. Settings holds what a user changes: Enabled, Show in bar, Setup, the fields and Keys. Details holds what a user reads: the description, the capabilities, the listing, Manage, Status and Requirements. Every opened page shows Settings, a change of the manager's rows keeps the page shown, and a page change returns the body to its top. A plugin with no setup screen, field, list or key still opens on Settings, which then reads "This plugin has no other settings." under its switches. A push or pop slides on `motion.duration.normal`, so a `motion.scale` of 0 makes it instant. Escape pops the page, then closes the window, while the window has the keyboard: the list leaves the key to the window host, which closes every application window on an Escape its plugin does not take. A plugin that leaves the manager's rows while its page is shown, as Remove's rescan takes it, returns the window to the list with a notice naming it.
- **Keyboard.** The page's strip is the Tab stop after the title: Left and Right change the page, and Ctrl+Tab steps it from any control. The list's search field is the initial focus. Printable keys typed elsewhere on the list focus the search field and append that text. The list cursor moves with Up, Down, PageUp, PageDown, Ctrl+Home and Ctrl+End, and Return opens the highlighted plugin. A row's inline switch takes no Tab stop because the plugin page's Enabled switch is the keyboard path. A page opened by a key focuses the back button with a keyboard focus reason, so the ring shows. A page opened by a click uses the mouse focus reason. Escape during an uncommitted text or key edit restores the shown value and stays on the page. A second Escape pops the page.
- **Manage.** The list's heading holds an Add plugin button, `add()`. An installed plugin's page holds Update and Remove buttons, `update(id)` and `remove(id)`; a bundled plugin's page draws neither, since a bundled plugin is disabled, never updated or removed. The terminal is a newer window, which Hyprland focuses and stacks over the Settings window, so the Settings window stays open behind it and its rows change once the command there ends. A refusal keeps the window open and stays on the page, or over the list for `add()`, as a setting's does. Omarchy's shell menu opens Add, Clone and Remove in a floating terminal so the warning and the confirmation stay visible (basecamp/omarchy `e332dc9`, `omarchy-menu-plugin`); VGS takes that rule and adds the update, whose question is the diff review.
- **Requirements.** Below the status, one `RequirementRow` per `requirements` row: the command, its state as a `Badge`, Present in the success tone and Missing in the danger tone, or the warning tone for an optional command, and the purpose under it. While one is missing, an Install all missing button calls `installRequirements(id)`, which shows the requirement notice for the plugin: it names each missing package, optional ones included, and its own Install runs one package manager's packages per press in a floating terminal, primary first, as [requirement-notice.md](requirement-notice.md) sets out under Install. A row draws no step of its own.
- **Status.** On Details, one `StatusRow` per `status` row, grouped as the fields are under `Status` and each group's heading: the label, the value in a `Badge` of its tone or as text, the hint and, while its value offers the entry's action, the action as a button with the command behind a `CommandDisclosure`, each such line a `StatusLine`. A `presenceList` row adds one line per item, with Connect, which opens a masked field and keeps the item's command behind its own disclosure, or Disconnect alone for an item that is a secret's presence. A button calls `act(id, key)`, `storeSecret` or `clearSecret` on the manager, and a refusal or a failed write reads under its line. A disabled plugin's rows, and an entry it has not published, read "Not reported". [status.md § Shown](status.md#shown) and [§ Actions and secrets](status-actions.md#actions-and-secrets) hold the rules ([D061](../decisions/D061-no-manual-commands.md)).
- **Setup steps.** A step, its button and the command behind Show command, shows only while its value offers it: a `presence` while `absent` and a `state` while it carries `action: true` or names one of its entry's `actions` ([status-actions.md § Actions and secrets](status-actions.md#actions-and-secrets)). `Steps.js` is the page's one rule for it: `statusStep` gives a status line its action and command while `PluginLogic.statusActionOffered` holds, `itemCommand` gives a `presenceList` item its command while its step is Connect, and `requirementApplies` shows Install all missing while a requirement is missing. An unreported entry and every entry of a disabled plugin draw neither, so a command never sits on a line without the button that runs it.
- **Setup.** On Settings, one button per TUI the manifest lists with an `entry`, drawn from the manager row's `tuis` with the entry's label and icon, so a setup screen needs no launcher search. A button calls the manager's `openTui(id, name)` ([manager.md](manager.md)), takes no press while the plugin is disabled, and a refusal reads under the buttons.
- **Show in bar.** A plugin that declares `bar-widget` and a kind besides `bar` and `bar-widget` has a Show in bar `Switch` under Enabled. It calls the manager's `setPlaced(id, placed)` with the opposite of the row's `placed`: off takes every layout entry of the widget off the bar, on puts one in its default section, and neither writes `disabledPlugins`, so the plugin stays enabled and its other kinds stay built. A widget-only plugin draws no Show in bar: unplacing it would disable it, so its Enabled switch is its placement ([placement.md](placement.md)). The switch takes no click while the plugin is disabled, and its hint says to enable it.
- **Its own page.** Once Settings is disabled no window is left to hold a button that enables it, so its own page shows the command that does behind a `CommandDisclosure` under the Enabled switch.
- **Fields.** One `SettingField` per schema entry, an inline `Field` whose row is a `FormRow`, in the manifest's key order, entries without a `group` first and each group under a `SectionHeader` in the order its first entry appears. A boolean uses a `Switch`. An enum with at most three options uses `SegmentedControl`; a larger enum uses `Select`. A string with `optionsFrom` uses a `Select`. A string or number with `presets` uses a `Select` with Custom… last when `allowCustom` is true. A custom datetime string shows a live preview and refuses an invalid format before it writes. A bounded number uses a `Slider`, and a `unit` labels the value. One `KeyField` per bind, a `BindField` of `qs.Ui` with the manifest's key under it, draws a `ShortcutField`: Return or a click captures the next pressed combo, its keyboard button types one as `MOD+KEY`, its clear button unbinds, and a hint names every other plugin shortcut and user Hyprland bind that holds the same key, and says when the user's binds could not be read ([D086](../decisions/D086-key-capture-passthrough-submap.md)). While a user bind holds the key, Use my binding unbinds the shortcut in one click, so the user's bind keeps the key: the System plan's Q3 choice, which `scripts/smoke/rows/sound.sh` presses on the Sound plugin's microphone mute key. A `list` entry ([plugin-manifest.md § Settings schema](plugin-manifest.md#settings-schema)) draws no field among the others: it has its own section after them, titled with its label, where `ListField` draws one group per item, its name beside a Remove button and each of its fields by `SettingField`, and an Add button that appends an item of the entry's `defaults` under the lowest whole number no item names. Each edit writes the whole list through the same setting write. A pad's key is a Keys row like any bind, with no default, so the row says so and draws no reset. A field shows what the configuration holds after every write, so a refused value leaves the old one in place, and the refusal stays on the page until a later call for that plugin succeeds.
- **Fresh state.** Each open calls the manager's `rescan()`. A command installed, or a setup run from a terminal, while the shell ran then reads as it now is: the scan updates each requirement's state, and its requirements revision makes each plugin's service read its own state again, as the Themes page's Browser theming row does ([theme-browsers.md § Chromium](theme-browsers.md#chromium)). The scan wakes every plugin that listens to the requirements revision: Displays reads its monitors again, and Jarvis, the theme follow and the system-step probes re-read their state. That is the cost of current state on each open, paid on a user action, never in a loop.
- **Payload.** `{}` opens the list and `{"plugin":"<id>"}` that plugin's page, through `vgshell ipc call shell summon window vgs.settings '<payload>'` or the plugin's own `open` IPC; the `surfaces` capability opens only its caller's surfaces, so another plugin links to a page through that command; an id no plugin has opens the list with a notice naming it, and any other key or a payload that is no object throws out of `open()`, which refuses the summon.
- **Layout.** The list page and plugin page compose `Pane`, [D050](../decisions/D050-container-layout-contract.md). The header, search field, row highlight, plugin description, section headers and field labels share one content edge. Each boxed row then uses its own padding for its icon and text. A field control starts after the label column and ends on the content edge. The scroll bar sits inside the right window inset, so the content right edge does not move when the page overflows. Each row's lines centre on its icon, and each field label centres on its control or value. `scripts/smoke/rows/manager.sh` reads both pages back through the probe's `descendantGeometry` and holds each within one pixel. The Status and Requirements rows are groups in a `GroupList`: a row's own lines sit `field.gap` apart, rows sit `groupList.gap` apart with a hairline between them ([design-layout.md § Groups](design-layout.md#groups)), and a read-only value draws in `text.value`, its label's pair. `scripts/smoke/rows/manager.sh` holds the Requirements groups' gaps and hairlines within one pixel, with a control per rule.

A string with `optionsFrom` gets its model from the manager row's `settingChoices`, not from an editor command. [status.md § Setting choices](status.md#setting-choices) defines automatic selection, unavailable ids and refreshes without configuration writes. `scripts/smoke/rows/settings.sh` reads each back from the fixture's drawn field.

## Invariants

1. The window lists every plugin `listPlugins` lists, itself included, with the same enabled state, and writes enablement, a setting and a key that reach `shell.json`, the running instances and the Hyprland layer. Enforced by `scripts/smoke/rows/manager.sh`, which also reads the rows' icon, source, capabilities, binds, requirements and errors back. Its Show in bar switch writes the widget's placement to `shell.json` and the bar's build records, and a plugin with another kind stays enabled; a widget-only plugin's page draws no such switch. Enforced by `scripts/smoke/rows/placement.sh`, which clicks the drawn switch and reads a widget-only fixture's page.
2. Update, Remove and Add plugin each open their core TUI, with the plugin's id for the first two, whose terminal Hyprland focuses over the window, which stays open, and update and remove hand no `--yes`, so the question stays on the terminal; Install all missing shows the requirement notice for the plugin over the window, which stays open; a bundled plugin's page draws no Update or Remove. Enforced by `scripts/smoke/rows/manager.sh`, which clicks each button and reads the argv a stand-in terminal records, the notice the core holds, the focused window and the client list, by `scripts/test-tui-logic.js`, whose controls are table copies that pass `--yes` to update or remove, a `managerTui` copy that updates a bundled plugin and `tuiShownAnswer` copies that refuse a focused live window or take another TUI's busy key for it, and by `scripts/test-notice-logic.js`, whose control is a judge copy whose request drops the optional commands.
3. The window is the token width, or the monitor's width less two gutters when that is less, and half the monitor's height, centred on the monitor's work area within one pixel, and it holds the keyboard once open. Enforced by `scripts/smoke/rows/manager.sh`, from the compositor's client list; the clamp row gives the nested output a 480 by 720 mode, since a headless output stays 0x0 in the sandbox.
4. A click on a row, the title's menu with typed letters and Enter, the back button, Escape, a deep link, the shortcut, the gear and a drag of the page's scroll bar each do what the page says, and a plugin whose directory goes while its page is shown returns the window to the list with its notice. Enforced by `scripts/smoke/rows/manager.sh` with the nested seat's pointer and keyboard; the page's control is a change of the rows that keeps its plugin, which keeps the page.
5. An edit in progress survives an unrelated configuration change: the same drawn field keeps its focus, text and cursor. Escape restores an uncommitted edit before a later Escape pops the page. Enforced by `scripts/smoke/rows/settings.sh`.
6. The window is a Hyprland window: its border, its focus, its keyboard and the dispatches that move, tile, float, focus and close it are Hyprland's. Enforced by `scripts/smoke/rows/windows.sh`, [surfaces.md § Invariants](surfaces.md#invariants).
7. A status action's button opens the plugin's own TUI or the requirement notice for its own commands, Connect and Disconnect store and clear the listed account through the core, and Show command reveals the command a step runs. Enforced by `scripts/smoke/rows/settings.sh`, `scripts/smoke/rows/manager.sh` for the page's own command, and each plugin's row, [status-actions.md § Invariants](status-actions.md#invariants) 1.
8. A mouse drag on a page leaves it where it was, while a wheel notch scrolls it Qt's step, a two-finger swipe moves it as far as a GTK list and Tab scrolls each focused row into view. Enforced by `scripts/smoke/rows/settings.sh`, whose controls give the page Qt's left-button drag and Qt's own swipe back, [components.md](components.md).
9. A setup step and its command draw only while the step applies. Enforced by `scripts/test-settings-steps.js`, each rule of `Steps.js` with a control; by `scripts/smoke/rows/settings.sh`, which reads a present token's row with no command, an absent one's with Set up token and Show command, and a disabled plugin's with neither, and whose control is a row copy that keeps a present entry's command and draws Show command; and by `scripts/smoke/rows/agent-warden.sh`, which reads no command anywhere on a healthy warden's page, Set up with its command while the warden is not set up, and Install all missing while vsys is missing.
10. Each open asks for a scan, so a status row that reads the system shows its current state. Enforced by `scripts/smoke/rows/themes.sh`, which puts a stand-in browser theme writer on the shell's PATH and reopens the window: the Browser theming row stops offering its install. Its control is a Settings copy whose `open()` asks for no scan, which leaves the row offering it.
11. A `list` entry's Add, Remove and item fields write the whole list to `shell.json`, and the page draws what it holds. Enforced by `scripts/smoke/rows/scratchpads.sh`, which makes and edits a pad through the drawn field, and by `scripts/test-pads.js` for the list's judge.
12. A plugin's page opens on Settings, the strip shows Details and returns by a click and by the keyboard, a change of the rows keeps the page, and a Setup button opens its TUI through the manager. Enforced by `scripts/smoke/rows/settings.sh`, whose control is a page copy that opens on Details and keeps its scroll, and by `scripts/smoke/rows/tui.sh`, which presses a fixture's Setup button and reads the manager refuse an unlisted script and a disabled plugin's.
