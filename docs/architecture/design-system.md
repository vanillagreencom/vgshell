# One token table and one component library draw every surface

Read before touching a token, the theme judge, `Theme`, a component of `qs.Ui`, a plugin-owned look, a pointer, keyboard or focus path, a Settings field, or text a user reads.

## The approach

Every view meets the polish of Vercel's web app or a standard modern consumer app. This is the organization's user experience principle (owner, 2026-10-06).

Every value a surface draws with comes from one table, `shell/Commons/Tokens.js`, read as `Theme.<group>.<token>`. One pure judge, `shell/Commons/ThemeLogic.js`, resolves a theme document against the table, and `Theme` publishes each group frozen ([D015](../decisions/D015-tokens-are-a-judged-table.md)). The user's Appearance values, shell.json `appearance`, resolve with it once, over the theme ([D104](../decisions/D104-appearance-values-over-the-theme.md)).

The component library `qs.Ui`, listed in `shell/Ui/qmldir`, is the only code that turns a token into a drawn pixel. A screen composes its components and draws no control of its own. A control extends a `QtQuick.Templates` type ([D017](../decisions/D017-templates-and-path-icons.md)), and an overlay is a Quickshell `PopupWindow` anchored to the item that declares it ([D018](../decisions/D018-overlays-are-quickshell-popups.md)).

Each input behaviour has one owner in `qs.Ui`. `PointerCursor` draws the pointing hand, `TouchpadScroll` moves a view under a touchpad swipe, `KeyNav` moves through a composite, `FocusRing` shows focus, `ListCursor` draws a list's selection and `Pane` owns a container's inset. The Keyboard, Motion and Layout rules below govern them.

A plugin whose design must look the same under every theme owns its look through an `appearance` table. The same judge resolves it, fed only the theme's mode, accent, motion scale, interface font and raised surface colour, except the standard surface `GlassSurface` draws while glass is off ([D023](../decisions/D023-plugin-owned-appearance.md)). A plugin's Settings page is drawn from its manifest schema ([D032](../decisions/D032-settings-plugin-and-manifest-settings-convention.md)). Text a user reads states the result and the action the user takes.

## Why

One table is the one place a value changes, so a theme restyles every surface at once. A literal value or a private control is a second style system: a theme change misses it, and it draws states nobody checked in the Gallery.

One owner per input behaviour lets one check cover every site. A keyboard, pointer or touchpad user then gets the same behaviour on every screen, and no screen locks one of them out. A list cursor shared by rows prevents a hover fill and a keyboard highlight from showing different selections. One container inset keeps boxed children and unboxed text aligned, with equal side insets when content overflows.

A plugin-owned look names the theme values its design takes as its only inputs, so no other theme value can leak into it. The motion scale is one of them because it is the reduced-motion control, not styling.

A schema-built Settings page gives every plugin a full page with no UI code and the same rows. Runtime choices let that page offer discovered devices, accounts or models without deleting a stored value when an offer disappears. A user reads a label once. A diagnostic key, a reason code, a format syntax or a command asks for knowledge or work the shell should carry.

## Rules

### Tokens

- Do read every colour, font, metric, radius, opacity and duration from `Theme`. `scripts/check-design-tokens.py` refuses a literal in shipped QML under its `literal-*` rules, and an unknown `Theme` path under `token-unknown`.
- Do publish every top-level group of the table as a read-only property of `Theme`. `group-unpublished` in `scripts/check-design-tokens.py` refuses a group left out.
- Never give the table or the judge an import, a Qt object or I/O, so a script runs the shell's own judge. `scripts/test-theme-logic.js` runs both under node.
- Do keep the shipped layout scale on the 4 px grid. `GRID_EXCEPTIONS` in `scripts/test-theme-logic.js` names the permitted classes, and that test walks every length token. Keep row heights independent of the control size scale, so changing buttons does not resize every list.
- Do give a component whose text differs from a shared type role its own role in the `text` group, a scale of `font.size`, and never change a shared role for one component: `item` and `itemHint` draw fields, selects and list items, and a menu entry draws in `menuItem` and `menuItemHint`. `scripts/qml-tests/tst_label.qml` pins every role's size.
- Do keep the shipped theme and every catalog entry readable at the floors `ThemeLogic.readabilityShortfalls` states. `scripts/check-theme-contrast.js` judges them.
- Do measure a drawn hint at its native pixel size against the fill directly under it. Use the median RGB of repeated straight-stroke interiors across the line. Keep the same sample positions before and after. Exclude stroke edges and isolated extreme pixels. Measure stem width as its summed coverage across the row, and sample the peak column's centre pixel only if that width is at least two pixels or both neighbours are below half coverage. Apply the text readability floor to that sampled ink and fill; a passing token ratio alone does not prove that the drawn hint passes. Repeat text that a reason covers, drawn at `Theme.opacity.disabled`, is exempt from the text readability floor while that reason shows. `scripts/test-theme-logic.js` pins the hint's rendering margin; captured Settings pages prove the drawn result.
- Do identify a labelled button by its label meeting the text readability floor; its resting border and transparent fill are not held to the boundary floor.
- Do keep a modal card the layer above the page its scrim dims, in every mode: its fill at least as light as the dimmed page or 3:1 against it, and its border 3:1 against it; where the scrim dims a wallpaper and no border colour holds 3:1 against it, the fill carries the layer at 3:1. `ThemeLogic.readabilityShortfalls` judges `dialog.background` and `dialog.border` over `color.scrim` on each resting surface.
- Do mark the item under the pointer with a line in its own colour where text sits on the scrim over a wallpaper: `carousel.hint` and `carousel.hintActive` are near one black or white there, so a colour change does not show. A closed tab under the pointer draws a line thinner than the open tab's (`Tabs` takes `hoverMark` for it) and a word draws underlined (`TextUnderline`); the open tab's indicator draws `carousel.tabIndicator`, the accent where it reads 3:1 on that backdrop and `carousel.hintActive` where it does not, and a chosen word keeps `text.bodyStrong`'s weight.
- Do rest a failure or status line over a wallpaper on a solid plate, `carousel.failurePlate`, a theme surface, never on the scrim alone, and lead it with the danger mark, drawing both in `carousel.hintDanger`: the theme's danger where it reads 4.5:1 on the plate and the theme's text colour where it does not. `ThemeLogic.readabilityShortfalls` judges the line on the plate, which `scripts/check-theme-contrast.js` runs on every theme, and `scripts/test-theme-logic.js` pins the rule and the plate and mark in each view.
- Do centre an icon that leads a line of mixed-case text on that line's x-height centre, half way between the baseline and the x-height (`Label.topForLeadingIcon`), on a device pixel. Mixed case carries most of its ink between the baseline and the x-height, so its capital centre reads high, and its line box centre, which holds the descent, reads low. A line in capitals or figures, such as an uppercase role, a bar reading or a level, keeps the capital centre: the label reads that from its own case and text, so a caller passes nothing. A single mixed-case line that is a text link instead centres between its highest glyph ink and baseline, excluding descenders, read by `FontMetrics.tightBoundingRect` through the same helper with `link` true. The actual Jarvis API keys “Remove key” action measured 1.59375 logical px below that centre before the change, or 3.1875 device px at 2x. The Google Drive “Remove” action read the same; “Sign out” read 2.09375 logical px below it, and the wallpaper “Show all” link read 1.40625 logical px below it. These are text-specific readings, never a fixed 2 px correction ([VGS-1966](https://linear.app/vanillagreen/issue/VGS-1966/an-icon-beside-a-text-link-sits-level-with-its-words), owner Slack 1792538331, drawn IPC geometry from `sandbox-shots` runs `actual-before-1x` and `actual-before-2x`, paired with `qml-unit` FontMetrics run `actual-font-metrics` on cachy, Qt 6.12.0, 2026-10-21). An empty or wrapped link keeps the general rule. An underline does not move the icon. An icon beside exactly two lines centres on the block, as `ListItem` does. Beside three or more lines, or a block whose detail count changes with content, it centres on the first line's reading through `Label.topForLeadingIcon`, so it stays beside the name it marks. Notification media, an image, faces, an application icon or a symbol icon, is no leading icon: it fills the card's media square, centred on the card whatever its lines, and an application icon and a symbol draw at one size (`look.media.icon`). `scripts/qml-tests/tst_notification_media.qml` pins it on cards of one and two body lines. This replaces the 2026-10-13 capital rule (owner, Slack 1792184728, 2026-10-16). `scripts/qml-tests/tst_label.qml` pins the placement at 1x and 2x, and `scripts/test-theme-logic.js` each site's call.
- Do draw rest, hover, pressed, focus, disabled and checked from their own tokens, each different from rest, and never draw hover or press on an item a click cannot change. A bar item or an icon button draws no hover fill. An icon button's glyph brightens from `color.textMuted` to the foreground. Keyboard focus keeps its focus ring, and press keeps a visible change. Review holds it; `scripts/qml-tests/tst_button.qml`, `tst_toggles.qml` and `tst_baritem.qml` pin the shipped controls.
- Never draw a fill or a border on an icon toggle, or a hover, press or checked fill or border on any icon button: its glyph rests in `color.textMuted`, brightens to the foreground on hover, dims on press and draws in the accent while on, and a state tone, such as the notifications header's warning, sets the glyph in its place. The shared `IconButton` draws this, so no surface replaces its background, and a plugin's own icon toggle, such as the launcher's Categories button, draws the same. A filled icon button variant keeps its rest fill, and a text toggle (`ToggleButton`, `WeekdayChipGroup`, the tray's manage row) keeps its checked fill. `icon-button-background` in `scripts/check-design-tokens.py` refuses an `IconButton` that replaces its `background`, in `qs.Ui` too. Review holds a plugin's own icon toggle, whose fill no check can tell from any other drawing. `scripts/qml-tests/tst_button.qml` pins the shared control.

### Appearance values

- Do resolve the user's Appearance values only in `ThemeLogic.withAppearance`, once, and read the result through `Theme`; a value the user has not set is the theme's. `scripts/test-theme-logic.js` pins that no value draws every package as before.
- Do set every token of a control from its one base by the fixed ratio in `ThemeLogic.APPEARANCE_RATIOS`, which holds every ratio, and apply a ratio to a user's value only. `scripts/test-theme-logic.js` pins each ratio.

- Do give a popover, a menu, a dialog or the OSD the radius `radius.glass` only while the user's `glass` is on and only where its radius would be 0, and keep a radius the theme or the user's Corner radius sets above 0. Never set `surface.radius` from it: a panel attached to the bar keeps the bar's square edge. `scripts/test-theme-logic.js` pins each case.

- Do set the interface font on `font.family.sans` and `font.family.caps` alone, so code and key names keep `font.family.mono`, and set no token from the terminal font, which the theme targets write ([themes.md](themes.md)). `scripts/test-theme-logic.js` pins both.

- Never take a colour as an Appearance value; colours stay the theme's ([D025](../decisions/D025-no-theme-override-layer.md)). Review holds it.
- Do draw a value that maps to a Hyprland option with `ValueSourceRow` ([D057](../decisions/D057-one-row-for-hyprland-mapped-values.md)). `scripts/qml-tests/tst_valuesourcerow.qml` pins its states.

### Appearance

- Do let a plugin own its look only through the `appearance` file its manifest names. `PluginLogic.validateManifest` refuses another shape, and `appearance-refused` in `scripts/check-design-tokens.py` refuses a table the judge refuses.
- Never read a `Theme` member other than `appearance` in such a plugin, and never name a path the look lacks. `theme-read` and `look-unknown` in `scripts/check-design-tokens.py` refuse both.
- Do bind the look once through `Theme.appearance`, read every value as `look.<path>`, and draw nothing on a null look. Review holds it.
- Never give a plugin-owned look a text size below the shell's smallest text role. `type-floor` in `scripts/check-design-tokens.py` refuses it.
- Do keep launcher detail text at least 4.5:1 against its own fill and at least 1.25:1 apart from its resting title as drawn, so the detail remains secondary text in every theme.
- Do draw a text shadow only to lift light ink off dark glass; dark ink on a light card draws none. Key the shadow to the ink in one token, never a per-theme copy, as the notifications' `text.lift` does. `scripts/test-notifications-logic.js` pins it.
- Do hand every `qs.Ui` component a plugin-owned look draws with the look's own values; a component left on its defaults draws the shared tokens. `GlassSurface` takes only the look's fill, rounding and elevation, and while glass is off draws the standard surface. Gap: no check reads which values a plugin hands a component.

### Components

- Do give every input a minimum and maximum width from theme tokens. Enforce these bounds in `qs.Ui` components and the shared form row. Wide windows keep controls on the value column's start edge. Never set a width limit in a page or plugin.
- Do compose `qs.Ui` components, and never write a private control for something a component draws. Review holds it.
- Do draw a surface's background, a panel's, a flyout's, a popover's, a menu's, a tooltip's, a dialog's or an OSD's, with `Surface` or `GlassSurface`, handing it the surface's own token group as `standard`, so the user's `glass` value reaches it. `glass-bypass` in `scripts/check-design-tokens.py` refuses a background read of such a group outside it.
- Do draw a key hint row with `KeyHints`: outlined key chips beside plain `hint`-role labels on the surface the row sits on, with no backing, shadow or token group of its own. `scripts/qml-tests/tst_layout.qml` pins it.
- Do add a new component to the Gallery in the same change, in every variant and state, with a focus example for a focusable control. `scripts/smoke/rows/gallery.sh` refuses a component `qmldir` lists that the Gallery lacks, and a missing focus example.
- Do disable a control the user cannot use now through its `disabledReason`, never `enabled: false` alone: one STE sentence that names the cause and the step, with no command and no internal word. The control stays a Tab stop, takes no click or key, draws faded, and shows the reason on hover and keyboard focus. A toggle that one user step unlocks also takes `unlock`, `{ label, run }`: a lock-open mark after it runs the step and shows the same reason. A panel header switch takes them as `switchDisabledReason` and `switchUnlock`. `scripts/qml-tests/tst_disabledreason.qml` pins the controls, and `scripts/check-disabled-reasons.py` lists every plugin site that binds `enabled` with no reason.
- Never give a decorative component, such as `VoiceOrb` or `QrMatrix`, a pointer handler, a process, a file, a cache or a secret store, so a passive layer that draws it stays input-free ([D026](../decisions/D026-passive-layers-are-a-capability.md)). `scripts/qml-tests/tst_voiceorb.qml` and `tst_qrmatrix.qml` pin it.

### Pointer

- Do declare `PointerCursor` in every element that takes a click, a plugin's `MouseArea` included, and never write `Qt.PointingHandCursor`. `scripts/check-pointer-cursor.py` refuses both under `cursor-missing` and `cursor-literal`; a `// pointer-cursor-exempt: <reason>` line exempts a click-away area or a scroll bar.
- Do set `acceptedButtons: Qt.NoButton` on every `Flickable`, `ListView` or `GridView`, so a mouse drag selects text instead of scrolling. `mouse-drag` in `scripts/check-pointer-cursor.py` refuses a view without it.
- Do declare `TouchpadScroll { view: <the view> }` in every view. `touchpad-scroll` in `scripts/check-pointer-cursor.py` refuses a view without it.
- Never scroll a list from the pointer's position. A hover may move the plate and a pick list's highlight. It never moves keyboard focus and scrolls nothing. A row scrolls into view on a key move through `KeyNav`, on a focus change from a click or Tab, because `ScrollArea` reveals the item that takes focus, on an opening and on an explicit jump. The header of `shell/Ui/layout/ScrollArea.qml` lists the inputs that scroll an area. A resting pointer at an overflowing menu's edge ran the menu to its end, one row a frame (owner report, Slack 1792188950). `test_a_resting_pointer_at_a_long_menus_edge_scrolls_nothing` and `test_a_hover_over_a_part_hidden_select_entry_scrolls_nothing` in `scripts/qml-tests/tst_overlays.qml` and `test_a_hover_at_a_scrolled_lists_edge_moves_no_keyboard_and_no_page` in `scripts/qml-tests/tst_devicelist.qml` pin it.

### Keyboard

- Never ship a click area without a keyboard path, or a focusable item without a focus indicator. `scripts/check-keyboard.py` refuses both, and `vgs-plugin check` runs it on a plugin tree.
- Do mark `// keyboard-path: <how>` or `// focus-indicator: <what>` only where a present mechanism supplies it; the marker exempts nothing missing. Review holds it.
- Do make a composite one Tab stop whose arrows move through `KeyNav`, and never let an arrow run an action. Review holds it; `scripts/test-key-nav-logic.js` pins `KeyNav`.
- Do let hosts own Escape and initial focus. Give a surface initial focus on its primary input, else its list, else its body, and never on an action that installs, removes or changes the system. Initial focus lands on the primary input, list or body with no ring. The ring appears after a keyboard navigation key. Review holds it.
- Never give the bar keyboard focus, except the focus grab that holds a widget drag until its release, or until the remove question takes the keyboard; a widget action has a global shortcut or a launcher path. Gap: no check reads the bar window's keyboard focus.
- Never give a passive layer the keyboard; the inbox is a toast's keyboard path. `scripts/smoke/rows/layers.sh` pins the layer host.
- Do keep a passive layer mapped, its content hidden and its mask empty, while a popup holds the keyboard grab, and unmap it once the last grab ends. Hyprland 0.56.2 `LayerSurface.cpp` `CLayerSurface::onUnmap` gives keyboard focus to `focusState()->surface()` when the unmapping layer had neither keyboard nor pointer focus, ignoring the xdg_popup grab, so an open list keeps showing while its keys go to the main window. `shell/Hosts/LayerHost.qml` holds the unmap while `OverlayState.grabs` is above 0, and `scripts/smoke/rows/layers.sh` pins it. Remove when a Hyprland release that VGS requires stops returning keyboard focus to the main window when an on-screen display closes while a popup holds it, checked against Hyprland's own changelog or code.

### Motion

- Do make every animation read a `motion` token, so `motion.scale` 0 stills the shell. `literal-duration` in `scripts/check-design-tokens.py` refuses a literal duration.
- Do stop an animation no duration drives, such as a shader clock, while `motion.scale` is 0. Review holds it.
- Do open and close a bar flyout with a Material container transform: fade plus a short slide from the anchor edge. `scripts/smoke/rows/surfaces.sh` pins the compositor placement and motion-scale stillness.
- Do give every list of clickable rows one `ListCursor`, which draws the one hover: a plate of `listItem.selected`, `listItem.selectedPressed` while pressed, that travels by `motion.list`, and the row it sits on draws its text, icon and secondary line in `listItem.selectedForeground` (`ListItem.lit`), on glass or not. Never draw a per-row hover fill or a list's own hover colour: `row-hover` in `scripts/check-pointer-cursor.py` refuses a colour that reads `hovered` or `containsMouse` in a list row. A menu's or a select's chosen entry keeps its check mark, and only `Menu` and `Select` move their selection on a hover. Use the shared row entrance and pass a plugin-owned look's timings and plate into the cursor. `scripts/qml-tests/tst_listcursor.qml`, `tst_list_hover.qml` and `tst_overlays.qml` pin it. A view's built-in highlight cannot replace the shared cursor: it supplies no easing curve and cannot serve rows in a `Column`.
- Do call `ListCursor.rebuilt()` when a list's rows change, as when its source publishes them again, and `disarm()` for a key step or an opening. The pointed row keeps the plate while it still holds the pointer's last reading, and a rebuild that moves it off that reading or removes it, before or after the call, hands the plate to the selection, so the plate never jumps to the selection while the pointer rests on a row or crosses the gap between two rows; a resting pointer takes no other row until it moves. A list whose model recreates every row on a publish keeps no row to hold: key it, as `ScriptModel { objectProp }` does. `tst_listcursor.qml` and `rows/list-motion.sh` pin it.
- Never declare a `ListCursor` in a `Column`, `Row`, `Flow` or `Grid`, which would lay the shown plate out as a row and move every row; declare it beside the positioner. `cursor-positioner` in `scripts/check-pointer-cursor.py` refuses it.

### Layout

- Do put each surface title in the shared `Pane` title slot. Keep its subtitle or description with the title. Leave `Theme.stack.titleSpace`, at least one body line, after the whole title block. Never add a private title margin.
- Do give a sticky footer equal padding on every side. Keep a sticky header's divider outside the body's viewport. Use the shared `Pane` geometry or the container's padding token, never a separate bar offset. `scripts/qml-tests/tst_pane.qml` pins the rule.
- Do mark a scrolled body under a sticky header, or over a sticky footer, with the `Pane` divider alone: one line from frame to frame. A `ScrollArea` draws no edge line. Never draw a line under a sticky header in a surface, a nested `ScrollArea`'s edge line included; scroll the body in the `Pane`. `test_one_line_marks_each_scrolled_edge` in `scripts/qml-tests/tst_pane.qml` pins it.
- Do put a pending-changes row in the shared `Pane` footer, pinned to the bottom of the System or Shell & Plugins panel. Never put it in the scrolling body; review holds it.
- Do use a centred modal for a timed trial or a confirmation the user must see, such as Keep/Revert. Never use an inline card; review holds it.
- Do compose `Pane` for every window, dialog, panel, popover and overlay, and never write a second inset. Align boxed children and unboxed text to its content edge. `scripts/qml-tests/tst_pane.qml` pins the box.
- Do clear a rounded corner through `Inset.clearing` in `shell/Commons/Inset.js`, and never hand-pad for a curve. `scripts/test-inset.js` pins the rule.
- Do let `ScrollArea` mark at rest each edge content continues past by fading the content toward what lies behind it. Never draw a line or a tint over the fade band, and never hide the fade behind hover or a scroll. `scripts/qml-tests/tst_scroll.qml` pins it.
- Do keep a container's scroll bar inside its right inset strip. `scripts/qml-tests/tst_scroll.qml` pins the gutter with and without overflow.
- Do fit dialogs and popovers to their content up to their maximum height share, then scroll. `scripts/qml-tests/tst_pane.qml` pins the fitted height.
- Do map every shell window centred across its output with its top at `size.window.topShare` of the output's height, and no taller than one cap: `size.window.tallHeightShare` of that height, or the room under that top when that is less. `OverlayState.windowRoom` owns the cap; the window host caps each window's map height at it, Settings holds its pages to it, and a window's content scrolls past it. The share picker maps once, at its Screens tab, at a height that holds every tab: the taller of its two hints, the longer of its screen and window lists, and the Area's controls. Past the cap it compacts its Area, then shrinks its preview no shorter than `size.preview.minHeight`, before it scrolls. A height change after the map goes through the compositor's `placeWindow`, so only the bottom edge moves. The launcher keeps its own layer anchoring (owner, 2026-10-18). `scripts/smoke/rows/settings.sh` reads the top at each tab and in the frames drawn during each change; `scripts/qml-tests/tst_overlays.qml` pins the cap, `scripts/smoke/app-window.sh` reads every window row's bottom against it, `scripts/qml-tests/tst_settings_window_height.qml` pins Settings' resize to it, and `scripts/smoke/rows/share-picker.sh` reads every tab's sources unscrolled for an eight-window request on a tall output.
- Do animate a summoned flyout's or panel's card height through `SurfaceHeight`. A bar flyout takes the room below its anchor at open, keeps that size while its content fits in it, never shrinks while it shows, and masks input to its card; a panel's layer covers its screen and catches the presses outside its card. A popup anchored inside a window, such as `Popover`, `Menu`, `Select` or `Tooltip`, follows its content, since a client cannot read where that window sits. `scripts/qml-tests/tst_surfaceheight.qml` pins the card; gap: no check reads which hosts compose it.
- Do leave `stack.heading` above every section heading, from the lowest drawn pixel above it to the heading's capital top, through the shared `Section`, which reads what the item above draws (`Theme.inkBelow`) rather than its box. The first heading of a page takes no space of its own: a tab page starts `stack.page` under its tab strip (`TabPages`), as a window's page starts under its title. Never pad a section in a page. `scripts/qml-tests/tst_section_spacing.qml` pins it on three plugin pages and a Setup tab.
- Do leave `stack.page` between two key/value rows in one column, from the bottom of the row above to the top of the row below, rather than their boxes. This holds for rows built on `Field`, a `SettingField`, a Settings field's stored key line and a `BindField` included, and for a bare `FormRow`, as in the Displays, Capture, Sound, Sounds, Keyboard and Windows panes and `ValueSourceRow`. The shared `FormRow` finds the row above and measures the space (`FormRow.rowAbove`, `FormRow.inkTop`, `FormRow.lineAbove`, `Field.lineBelow`) for both; a `Field` takes it as its top padding, and a bare row takes it above its row box. A control counts as drawn (`Theme.inkAbove`, `Theme.inkBelow`); a text line, a label, a text value, a field's lines or its hint, counts from its capital top to its font's descent line, or to its baseline in a role drawn in capitals, not by the glyphs it holds, so rows of text keep one pitch whatever they read, and the underline of a link inside running text still counts. A segmented control, a select, a switch, a slider, a hint line and a stored key's line under its field then leave the same space, and each row box stays `row.height`, so two boxes may overlap where their controls draw less than the box. A row under anything else, such as a section heading, a group list or a block of the page, keeps that item's own spacing, and the groups of a `GroupList` keep its gap. Never space a row by hand or per control. This supersedes the VGS-1363 owner ruling (Slack 1791704028) that ink is measured only above section headings, on the owner's word for Settings rows (Slack 1792188454). A control a row holds declares where it draws when that differs from its box, as `Slider`, `Switch`, `LevelSlider` and `SavedSlider` do; a plugin's slider with a reading beside it is a `SavedSlider`. One site keeps its own slider, with its own ink: a Settings number field (`SettingField`, VGS-1761). A row a `Repeater` moves stands under the row now above it: the search reads each row's place in its column, and of a bare row above only values that row computes itself (`rowShown`, `belowLine`), since Qt 6.11.2 keeps a binding's trigger on geometry it read before and a moved row would loop. `scripts/qml-tests/tst_settingfield.qml` reads the gaps of `Field` rows and of bare `FormRow` rows, the text rows' pitch and a reordered column from the rendered image and the rows. Gap: a `Field` and a column of one setting's rows, such as a `SettingField`, declare no `rowShown` or `belowLine`, so a row under one reads its geometry; the reorder reading passes for fields, and no check covers a reordered `SettingField`.
- Do draw a list of groups, such as a Status section's entries, the Setup tab's steps and keys, the Requirements rows or a log's records, with the shared `GroupList` of `qs.Ui`: groups `groupList.gap` apart by their line boxes, less how far a heading over its own group list starts its ink below its rows', so a drawn-ink reading of a gap may differ by the descent, and a hairline in each gap, centred between the lowest drawn pixel of the group above and the highest of the group below (`Theme.inkBelow`, `Theme.inkAbove`), the gap above a filled button included. Never space or divide such a list by hand. `scripts/qml-tests/tst_grouplist.qml` pins it from the rendered image.
- Do give a popover list no outer inset; its row fill meets the border and its row padding carries the text inset. `scripts/qml-tests/tst_overlays.qml` pins it.
- Do leave one blank row between blocks in a floating terminal: a cleared screen starts its first block on row 0, and one blank row stands under the logo. Draw each block through `bin/lib/tui.sh`, whose gap mark owns the blank row and takes the logo's row from `bin/vgshell-tui`; never print a blank line of your own. `scripts/test-tui.sh` pins it in "a header starts with one blank line", "two questions and a step after them share one blank line", "a step on a cleared screen starts on its first row" and "a header under the logo draws no blank line", and `scripts/test-vgshell-tui.sh` in "one blank row stands between the logo and the first header".

### Copy

- Do use an icon button's label as its tooltip: two or three words naming its action, with no explanation. Bar widget status readings keep their status text.
- Never let a tooltip cover a sibling label, or the control and buttons of the row it explains. An item with a label under it opens its tooltip to the right (`Tooltip`'s `side: "right"`, `IconButton`'s `tooltipSide`). A form row's explainer may cover its own row's hint, never another row's text, its control or its buttons: with no room past its control, or where it would clip the hint there, it opens under the row, over the hint from the hint's top (`side: "belowStart"`), on the value column beside a label focus ring that reaches the hint. That band draws a lifted fill with no outline, so it never reads as an empty input. That band is one line, the room the hint's top leaves above the next row. A row with no hint has no line of its own under it, and an explainer too long for one line of the value column would run onto the next row, so there the label opens nothing and the row's info button holds the explainer for its dialog. A form row's info button opens no tooltip, which would lie on the next row's label: a press opens its dialog. `scripts/qml-tests/tst_button.qml` pins both sides, and `scripts/qml-tests/tst_formrow.qml` and `tst_bindfield.qml` the row's. A disabled control's reason (`side: "clear"`) opens beside its control where it covers no text, image or Tab stop of its window, inside the box the window's content spans, and where no place is free, where it covers the least, a place inside that box that covers no Tab stop first; `scripts/qml-tests/tst_reasontip.qml` pins it. A text that opens with the reason's words may declare `repeatsReason: true` so the reason can cover it while every other text, image and Tab stop stays clear. Beside a control over repeat text means on that text’s rows under the control, with the whole text at `Theme.opacity.disabled` while the reason covers it.
- Do let the pointer and the keyboard reach a link in a tooltip. The tooltip stays open for `tooltip.delay` after the pointer leaves its item and while the pointer is on the tooltip. The item keeps the keyboard: Tab moves to the link and draws its focus ring, 2 px clear of its words as every link's is, and the item draws none while its link is current, so one ring shows where the next key goes; Enter, Return or Space opens it, a further Tab goes on to the next item, and Escape closes the tooltip. A tooltip with no link closes when the pointer leaves its item and takes no key. `scripts/qml-tests/tst_tooltip.qml` pins it, and `scripts/smoke/rows/bar.sh` the real pointer and keys.
- Do write text a user reads in ASD-STE100 Simplified Technical English. Name the result of a check or the action the user takes, never the internal operation. Review holds it.
- Do keep a plugin description to one or two short sentences with no feature list, and a hint to one sentence; longer help goes behind an `InfoButton`. Review holds it.
- Do give a field a hint only when the user cannot act correctly without it: a limit, a side effect or a condition the label does not say. Never restate the label; a hint whose words all stand in its label says nothing, and a hint that only describes what the control does is removed. Any further explanation goes behind the field's info icon, kept short, with a line break where it helps. Owner rule, 2026-10-19 (Slack 1792469888 and 1792470048). `bin/lib/check-manifests.js` refuses a hint whose words are all in its label; review holds the rest.
- Do make the help behind an `InfoButton`, a field's `info` included, say what the setting is and what the user does with it, in words a new user understands. Never describe what the shell or a plugin does inside: "Jarvis checks the folder again when you press Talk." tells the user nothing they can act on. Owner rule, 2026-10-16 (Slack 1792182387.487899 and 1792182511.072549). Review holds it.
- Do end a Settings hint of one sentence without a full stop, and end each sentence of a longer hint with one: "Jarvis decision (2026-10-13, delegated authority): a one-sentence hint ends without a full stop; a hint of two or more sentences ends each sentence with one." `PluginLogic.validateManifest` refuses a hint that breaks it, and `scripts/test-plugin-logic.js` pins the judge.
- Do keep diagnostic keys, reason codes and command errors in the log, and map a plugin's own messages to a plain sentence before the plugin shows them. A user's own commands and their output stay unchanged. Review holds it.
- Never tell the user to run a command ([D061](../decisions/D061-no-manual-commands.md)). `scripts/check-user-commands.py` refuses the text.
- Do make text that names another VGS page, tab or section a link that opens it: use only the page reference form, `[words](page:<plugin id>/<tab>)`, or `[words](page:<plugin id>/Settings/<field key>)` for a Settings field, which `LinkText` draws as the link and Settings opens from a description, a hint or a status text, at the field for the second. A link's ring holds its words and the punctuation against their end, and stands 2 px, `focusRing.offset`, clear of them and their underline on every side. Text at rest keeps its spacing after a link; before one, narrow no-break spaces are added where the font's word space is narrower than the ring's room, `focusRing.offset` plus `focusRing.width` plus one pixel, or where no space stands there. `scripts/qml-tests/tst_linktext.qml` pins it. A bar item's tooltip draws the link too, and its widget opens the page through `frame.openPage`; any other tooltip draws the words alone. A plugin view opens the page through `shell.surfaces.openPage`, and a notice sends the reference's words, which a notice card draws as the link and a click on the card opens. A terminal line cannot link, so it names the button that opens the page. `page-reference` in `scripts/check-user-commands.py` refuses the plain words, `page-reference-target` refuses a literal target with no plugin directory, and `scripts/smoke/rows/settings.sh` pins the click.
- Do make text a user reads that names a file or folder a link that opens it in one click. Owner rule, 2026-10-16 (Slack 1792189443): "any time we cite/reference a file, link it so it can be opened". Review holds it. Use `PageReference.fileReference(words, path)` from `shell/Commons/PageReference.js` to write `[words](file:<percent-encoded-path>)`. The angle brackets mark a placeholder, not target characters. The helper applies `encodeURIComponent(path)` and also encodes parentheses, so spaces, parentheses and a literal percent reach the opened path unchanged. The decoded path is absolute, under `~/` or relative to the configuration directory; a folder ends in `/`. When the text has no matching explicit `link`, `LinkText` draws each page or file reference as its own link, and each link activates its own target. A status action of route `file` can also supply a step's Open file path when the user chose its folder. Settings, a tooltip, the core notice and a notice card open a file through the one core route, `shell.tui.edit` (`PluginLogic.editRoute`, `TuiRunner.openPath`), which reads the file's content type with `gio info` and splits by it: a text file, any `text/*` type and the text formats the editor takes (JSON, TOML, YAML, XML, shell), opens in the core editor TUI, any other file, such as a PDF, a spreadsheet or an image, opens in its default application with `gio open`, and a folder in the file manager. A path that does not exist starts nothing and answers `refused: file=<path> reason=missing` to the `done` its caller passes, which shows that the file is no longer on this computer, as the Google Drive popover's row does and a notice card does (it stays, and a notification says why, as it does for an editor busy with another file); `Plugins.openReference` hands that `done` on from `shell.surfaces.openPage` and a bar widget's `frame.openPage`, so no caller learns of a refusal only from the log; a program (an executable or an AppImage) opens nowhere. No surface keeps an open path of its own. `scripts/test-page-reference.js`, `scripts/qml-tests/tst_linktext.qml`, `scripts/test-tui-logic.js` and `scripts/test-settings-steps.js` pin it.
- Do give a step, notice or status line that states a limit, a size, a count or a time, an info icon that says why the limit exists, in words a new user understands. Owner rule, 2026-10-16 (Slack 1792189443). Review holds it.
- Do underline a link that stands on its own only while the pointer is on it, and a link inside running text at rest and on hover. Owner rule, 2026-10-19 (Slack 1792451091), split by Jarvis decision 1792464386-2557738-17858 so colour is never all that tells a link in a sentence from its words (WCAG 1.4.1). A link stands on its own when it is a `RowAction`, a `LinkText` whose link is its whole text, a notice card's page link whose words are the whole body (`ImageText`'s `underlined`, while the pointer is on its card) or a word that acts on the scrim (`TextUnderline`); any other `LinkText` link, and a notice card's link in its body, is inside running text. Keyboard focus draws the focus ring alone. On hover the underline keeps the resting thickness, the font's line width or `rowAction.underline`, and grows no thicker. Spacing reads the ink drawn at rest: the underline of a link inside running text, and the words of a link that stands on its own, whose hover underline draws in the space under them, so a hover moves nothing; the focus ring still holds the underline's room. Keep one clear device pixel row between the underline and the lowest ink of the descenders g, j, p, q and y, and place the line as close as that row allows, wherever the baseline falls inside a device pixel: `Inset.underlineTop` derives it from the letters' depth (`DescenderInk`) and the screen's device pixel ratio, so no glyph touches the line at any scale or size. In Inter Variable at 13 and 15 px that is 5 px under the baseline at 1x and 8 device px at 2x, 2 device px closer than the font's descent placed it. Jarvis decision 1792451829-3591639-28142 (delegated authority). Never underline a link with `font.underline` or `<u>`, which Qt draws at rest where a descender meets it, and never draw a link with Qt's own anchor: `link-underline` and `link-unshared` in `scripts/check-design-tokens.py` refuse the forms its help names. Review holds an underline a plugin draws as its own item, which no check tells from other drawing. `scripts/qml-tests/tst_linktext.qml`, `tst_rowaction.qml` and `tst_imagetext.qml` pin rest, hover, focus and the underline's top at 1x and 2x for both kinds of link, and `scripts/qml-tests/tst_section_spacing.qml` the spacing under each.
- Follow [D075](../decisions/D075-consumer-features-need-no-developer-setup.md) when a setup step needs the user. Review checks the Settings path. Features without that path do not ship.

### Settings pages

- Do show a bind row with no info icon where it has a hint line, as a Settings key row has: its explanation opens in the shared tooltip over that line on label hover and keyboard focus while it fits one line there. A longer one, and that of a bind row with no hint line, as in Key Hints, opens in the row's info icon's dialog, since a tooltip there would lie on the bind under it.
- Do give each icon of a bind row one condition the user sees on the row, and keep its place, shown or not, so the row keeps one width: the keyboard on every editable row, checked while the typed entry is open; the clear button while the key edited holds a key and the typed entry is closed; on a Settings key row, the add button while the typed entry is closed, and last the reset while the keys differ from the default line under the row, so a row with the default keys leaves no gap between its icons. While the row listens, the box counts down the seconds Hyprland passes the keys through, and the end of listening shows no message. `ShortcutField` and the Settings `KeyField` state the conditions in their headers; `scripts/qml-tests/tst_shortcutfield.qml` and `tst_settings_edits.qml` pin them.

- Do put a switch on its label's row in the value column, never below the label; review holds it.
- Do give a plugin page one tab per kind of item, and declare each item's place in the manifest, never infer it from its label, group or plugin name:
  - Settings: "there should be no row that is not some sort of value a user can modify. That's the whole point of a 'setting'." Owner rule, 2026-10-16 (Slack 1792189351). A Settings row is a value the user changes on that row: the page's own Enabled, Show in bar and Show on the bar switches; a schema control, a string, number, boolean, enum or list; a stored key in a masked field the user stores, replaces or removes, a `presenceList` of a plugin that declares `secrets`, beside the field its `setting` names; a list of rows the user adds and removes, a `rows` entry with `settings: true`, after the fields; or a shortcut in the Keys section. A list item shows only its declared fields and its remove action, and never its storage key (`scripts/qml-tests/tst_listfield.qml`). Settings never holds a status chip, other than the chip of a listed row that needs the user, a status reading, a presence check, an instruction, a tools line or a free action; a stored key's field alone shows whether its key is stored, beside its Add key, Replace and Remove. A field for hardware a machine may lack declares `shownWhen`, a `presence` status entry of its plugin, and draws only while that entry reads present, so it draws neither before the service's first publish nor while the plugin is off. The links that open more values end the tab, since what they open is values: a configuration screen's (`entry.settings: true`) More settings text link, then, for a plugin a pane holds, More settings in that pane's holder, last.
  - Setup holds every install or setup step of the plugin, required or optional, and the keys a required step needs beside that step (`step`), drawn as the step's own lines under it. Steps that need something a new user cannot know how to make, such as keys from another site, open with the manifest's `setupGuide` callout, whose link opens the README section that guides them (`Callout`, `PluginLogic.setupGuideRow`); `bin/lib/check-manifests.js` holds its anchor to a heading of the README.
  - Details holds readings, never steps: each status reading in its own group, the optional tools, automatic alternatives included, as a reading in its Tools section, and the task screens in its Actions row. A status entry that offers an `action` or an `aside` and is no `rows` list is a step and stands on Setup. Owner rule, 2026-10-19 (Slack 1792469982). A line that reads whether a key is stored, with no masked field, is a Details reading. A reading that is a name, such as the address of the account signed in, declares `plain` and draws as text while it needs nothing, a chip only while it needs the user, as a listed row's state does; `scripts/test-plugin-logic.js` pins the tone it draws in. A reading the plugin has not published reads Not reported, since a plugin may leave one unpublished for good, save a reading that offers a core system step, which reads Checking… while its plugin is on and started: the core lends the step no reading until its first probe ends, and the plugin publishes the entry then. `scripts/test-settings-steps.js` pins both readings.

  `PluginLogic.validateManifest` refuses every other Settings placement and names the key: `setting` on a status entry that is no stored key list, `settings` on one that is no `rows` list the user changes through its actions, schema type `action`, a requirement's `setting`, `tui.<name>.entry.setting` and `hintFrom`. `scripts/test-plugin-logic.js` pins the refusals, `scripts/test-settings-steps.js` the Settings placement, and `scripts/qml-tests/tst_settings_setup.qml` a Settings tab that draws no chip.
- Do keep every required step on Setup after completion. Its chip reads Done in the success tone, To do in the warning tone, or Not available in the neutral tone. A step that is not done and that the user can finish reads To do, names the one action the user takes, and offers it as the step's `RowAction`: a link, a button, Open file or a page link. A step the user cannot act on reads Not available, says in plain words why there is no action and what will change that, and links the page where that change happens when one exists. Never show a To do step with no action. Declare each chip word once, in `shell/plugins/vgs.settings/Steps.js`, so the owner changes a word in one place. Order steps that are not done before Done steps, each in manifest order. Owner rule, 2026-10-16 (Slack 1792182387.487899 and 1792182511.072549): "we should not tell people something is not done, or todo, with no clear path for them to do it." Among the steps that are not done, To do steps come first, then Not available steps. The plugin's state value says a step is Not available with `available: false`, its `hint` saying why and what will change that; the status judge admits it only on a required step that is not done, offers no action and carries that `hint`. A step the plugin has not reported reads To do with Checking… under it while the plugin starts. While the plugin is on but could not start, because its build failed or another plugin holds what it needs, the step reads Not available with the plain line of why and no action, since turning the plugin off and on changes neither. `scripts/test-settings-steps.js` pins the Done, To do and Not available reading, the order and the actions; review holds the explanation.
- Do draw every Setup action as a `RowAction` text link. Draw no boxed action and no separate Requirements section on Setup. Collapse required tools into one Tools step, Done when all are present and current. Its To do explanation names missing or outdated tools. Its action opens the existing notice for all missing or outdated tools of the plugin. A required step that a missing or outdated required tool blocks offers that same Review action on its own row, with no second install route: its value names `action: "tools"`, which the status judge admits only on a required step of a plugin that declares a required tool, and the row draws Review only while a required tool is missing or outdated. `scripts/test-settings-steps.js` and `scripts/qml-tests/tst_settings_setup.qml` pin it.
- Do keep an optional step, an install or setup step the plugin works without, on Setup. Its chip reads Optional in the neutral tone while it is not done and Done once it is, it names its one action as any step does, and it follows the To do steps. It never raises the warning icon or Setup needed, and an optional step the user cannot act on reads Not available. The optional tools are one such step, Optional tools, with the Review all missing or outdated tools action. Owner rule, 2026-10-19 (Slack 1792469982). Gap: `Steps.js` has no Optional chip, steps with an action, such as Automations' Enable while logged out, Capture's Set up screen sharing and Install languages, the AI Usage sign-ins and the optional tools, still stand on Details, where `scripts/test-settings-steps.js` pins them, and no check refuses a step on Details; [VGS-1958](https://linear.app/vanillagreen/issue/VGS-1958) brings the pages and `Steps.js` in line.
- Do mark unfinished required setup with the same `Steps.setupNeeds` reading in the Plugins list and the Setup tab. The list shows Setup needed and opens Setup. The tab shows a warning icon in `color.warning`. Remove both marks when no required step reads To do, or the plugin is off; a Not available step raises neither mark. Optional tools add no setup mark. A plugin with required steps keeps its Setup tab when they are done. `scripts/test-settings-steps.js` and `scripts/qml-tests/tst_settings_setup.qml` pin the shared reading.
- Do show a key once, in a masked field with the existing keyring storage. Its field gives its source and the feature it unlocks, as D075 requires. `scripts/qml-tests/tst_grouplist.qml` pins the key field.
- Do keep each setting in its settings group. If a setting applies to the whole group, say so in its help instead of placing it above the group; review holds it.
- Do give bar widgets with like settings one order: a widget that offers `layout` groups every field, leads with the Readings group, and starts it with the shared fields it offers in the order `layout`, `labelStyle`, `refreshSeconds`. `bin/lib/check-manifests.js` refuses another order.
- Do declare a plugin's settings in its manifest schema, and never ship page code for its Settings page. `scripts/test-plugin-logic.js` pins the schema.
- Never make a user type a library's format syntax. Declare `presets` or `optionsFrom`, and judge a format string before writing it. `PluginLogic.validateManifest` refuses a string setting without either, and `scripts/test-setting-values.js` holds the format judge.
- Do feed `optionsFrom` from a `choices` status entry of the same plugin, with stable ids and labels. The first offered choice stands for the unset value and reads as its own label, so offer first what the unset value resolves to, such as a "System default" entry. A setting whose unset value means nothing is chosen declares `placeholder`, and the select reads it instead of an offer. Keep a configured id that leaves the offers and show it as unavailable, or under Custom… when the entry declares `allowCustom`; a `hideEmpty` field alone draws nothing while nothing is offered, whatever is configured. `scripts/test-plugin-logic.js` pins the schema and `scripts/test-plugin-status.js` the `settingChoices` model.
- Do use the shared Settings row height token for every inline setting's row box, so labels centre alike, and space the rows, each built on `Field`, `stack.page` from the bottom of one row to the top of the next, a control as drawn and a text line by its font, as § Layout sets out; this supersedes the VGS-1363 owner ruling (Slack 1791704028) for Settings rows. `scripts/qml-tests/tst_settingfield.qml` pins the gaps on a page of every Settings control.
- Do write a setting's label to fit the label column: it wraps there and never draws an ellipsis in any theme or scale, and at the default theme it fits two lines of the column, beside its info mark when it has one. Give a label that needs more words a one-sentence `tooltip`, which the label shows on hover and keyboard focus; longer help stays in `info`. `PluginLogic.validateManifest` refuses a longer label, `scripts/test-plugin-logic.js` pins the judge, and `scripts/qml-tests/tst_settingfield.qml` holds the judge's line count to the drawn label and pins the tooltip.
- Do draw the action of a key/value row as a `RowAction` right after its value: accent body text, underlined on hover. Never put a boxed `Button` in such a row. Set two or more actions of one row in `RowActions`, `rowAction.gap` apart. `scripts/qml-tests/tst_rowaction.qml` pins the control and the gap; review holds its placement.
- Do draw a `rows` status entry as a section of its own, the list full width under its label: one `ListItem` per published row that takes no click (`clickable: false`), so a row draws no hover, no press and no pointing hand, led by the entry's `icon`, with the row's label, its secondary line and, at its end, its state, plain text for a calm state and a `Badge` only for a state that needs the user, the warning or danger tone, then its row actions as `RowAction`s, each with its own hover, pointer, keyboard focus and click. A row's danger action without an `icon` draws the trash mark alone, its ink ending on the list's edge, and its text names the row. The entry's own action, such as Add, stands under the list, then the entry's hint and the reply to the list's last press. While the plugin is off, the list says so; on Details it also offers Turn on, and on Settings the Enabled switch is the one Turn on. A row action opens its declared TUI with the row's id as its one argument. `scripts/qml-tests/tst_settings_rows.qml` pins the drawing and the act, and `scripts/test-plugin-logic.js` the judge.
- Do mark every danger action, in the theme's danger colour, so it reads apart from an accent action by more than colour: an action that removes the item its row shows draws the trash mark alone, its label its tooltip and accessible name (RowAction's `removesItem`); another remove action leads its text with the trash mark; and a danger action that removes nothing, such as Sign out, leads its text with its own mark, a manifest action's `icon`. Owner rule, 2026-10-16 (Slack 1792184728): "the trash icon is enough". `scripts/qml-tests/tst_rowaction.qml` pins the three marks, and `scripts/test-plugin-logic.js` the refusal of an `icon` the shipped set lacks.
- Do put a row's description, its lines, hint or error, on its own lines under the row's value. The next key/value row starts `stack.page` under the last line's ink, as under any row; any other item starts the group space, `stack.group`, under that line, which `Theme.subTextRoom` gives in `Field`, `FormRow` and `SettingField`. `scripts/qml-tests/tst_spacing.qml`, `tst_formrow.qml` and `tst_settingfield.qml` pin it.

## Revisit when

A value a surface needs cannot be a token; a surface needs an input or keyboard model the shared owners cannot express; a plugin-owned look needs a sixth theme input, or a theme must restyle it after all; a Settings field needs a control the manifest schema cannot declare. A child must draw outside its container inset, a list needs several selection plates, runtime discovery outgrows the bounded choices list, or the owner changes the layout grid.

## Not governed

The theme package format, apply and targets, which are [themes.md](themes.md). The compositor-side capture of keys, which is [hyprland.md](hyprland.md). Each component's properties, signals and key handling, which are its file header, its test under `scripts/qml-tests/` and the vgs-plugin skill's API reference. A plugin-owned look's own values, which its appearance table holds. Developer logs, code comments, developer documentation and machine-readable output, which stay technical; a Gallery preview may name the component, property or state it shows.
