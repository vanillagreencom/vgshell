# Nightly run

Covers: .github/workflows/nightly.yml

The scheduled run of `scripts/validate` on GitHub. The check selector and its rows are [validation.md](validation.md).

`.github/workflows/nightly.yml` runs `scripts/validate --full` on `main` for every area but `qml` at 10:00 UTC and on a manual dispatch. No push, pull request or merge queue starts it, and no merge reads its result. The job runs only when the repository variable `NIGHTLY` is `on`, which is set while the repository is public; while it is private the job is skipped and the local runs of `scripts/main-run.sh` cover every area. Each area is one job that runs `scripts/validate --full AREA`, so the workflow holds no check of its own.

- `offline` and `unit` run as an unprivileged user in an Arch Linux container, which installs Quickshell 0.3.1 and Qt from the Arch repositories. The container is privileged because the Jarvis rows' private environment mounts its own `/proc` in a user namespace (`scripts/lib/jarvis-env.sh`). It runs an init process, `--init`, because the first process GitHub starts in a job container, `tail -f /dev/null`, reaps no orphan, and the rows that check a stopped process group read its zombies as still running. For the same reason the job lifts Ubuntu's AppArmor restriction on unprivileged user namespaces. The two Jarvis actual-model rows need prepared models (`JARVIS_LOCAL_MODELS`, `JARVIS_LOCAL_PYTHON`) that the runner does not have, so `offline` reads `could not run` there every night and names those two rows.
- `package` and `nix` run on the Ubuntu runner itself. Their scripts start their own containers through rootless podman, which does not run inside a container job.
- `qml` does not run there. Hyprland 0.56 allocates buffers only through GBM on a DRM device, and its headless backend opens none (aquamarine 0.15.1, `src/backend/Backend.cpp`: `Cannot open backend: no allocator available`). A hosted runner has no `/dev/dri`. In an `archlinux:latest` container with no DRM node, `HYPRLAND_HEADLESS_ONLY=1 Hyprland` aborted with `CBackend::create() failed!` (2026-10-04). The `qml` area stays with the local nightly run, `scripts/main-run.sh qml` ([D100](../decisions/D100-validation-selects-by-inputs.md)).
- Each job writes the area's verdict, exit status, seconds and failing `validate:` lines to the run summary. Exit 77 reads `could not run` and fails the job, as exit 1 does. The workflow opens no issue and posts nowhere.
