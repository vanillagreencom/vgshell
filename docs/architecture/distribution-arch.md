# Arch packages

Covers: packaging/arch/, packaging/aur-known-hosts, scripts/arch-packages.sh, scripts/publish-aur.sh, scripts/test-publish-aur.sh

This file holds the two Arch recipes, their AUR publication and their container test. [distribution.md](distribution.md) holds the licence, the version, the install tree and the recipe check every channel shares.

- `packaging/arch/vgshell/` is the release package and `packaging/arch/vgshell-git/` the development package, built from `main`. Each holds a `PKGBUILD`, the `.SRCINFO` that `makepkg --printsrcinfo` prints for it, and the scriptlet `<pkgname>.install`. Both are `arch=('any')`, with the licence expression from [distribution.md § Licence](distribution.md#licence). Their `package()` runs `packaging/install-system.sh` with `PREFIX=/usr` and `SYSCONFDIR=/etc` and has no `build()`. So each package ships the browser theme writer `/usr/bin/vgshell-browser-policy` and its sudoers rule `/etc/sudoers.d/vgshell-theme-browser`, which lets every user recolour Chromium-family browsers with no setup step ([theme-targets.md](theme-targets.md)). `scripts/check-packaging.js` refuses a `package()` without that line. The rule is not in `backup`: it is the package's grant, not a file the user edits, so an upgrade replaces it. The same install adds the XDG autostart entry `/etc/xdg/autostart/vgshell.desktop` ([distribution-autostart.md](distribution-autostart.md)), also outside `backup`: a user turns it off with their own entry of the same name under `~/.config/autostart`, which the package never touches.
- `depends` and `optdepends` are hand-written and identical in both recipes. The [recipe check](distribution.md#recipe-check) requires every required command from the core and shipped plugins, plus declared runtime libraries and data. AUR-only requirements are hard dependencies that the AUR helper resolves. A tool with a version floor in the `preflight_floor` table of `bin/vgshell` ([runtime.md § Process](runtime.md)) carries that floor as a `>=` constraint: `quickshell>=0.3.1`, `hyprland>=0.56`, `nodejs>=18`. Each optdepend names the feature that needs it after its colon. No recipe conflicts with a notification daemon.
- `vgshell` takes the release tarball, `vgshell-<version>.tar.gz` of the `v<version>` release, and `pkgver` is `VERSION`'s line. Its `sha256sums` is `SKIP` while the tag `v<pkgver>` does not exist, because no tarball exists to sum. After the release uploads the tarball, the recipe pins its sha256. `scripts/check-packaging.js` refuses `SKIP` once the tag exists.
- `vgshell-git` has no `source`. makepkg clones a `git+` source as a mirror, every ref the remote advertises, and GitHub's `refs/pull/*` still reach history that no branch holds. Its `prepare()` runs `git clone --filter=blob:none --single-branch --branch main -- "$url.git" "$srcdir/vgshell"` instead: every commit and tree of `main`, the tags that point into it, and only the file contents of the commit it checks out. `scripts/check-packaging.js` refuses a `source`, a `url` other than the repository's and a `prepare()` without that line. A depth-1 clone would cut the commit count `pkgver()` reads. The `--devel` check of yay and paru reads `git+` sources only. paru drops its `vgshell-git` entry on the next build, so it reports no new commit. yay keeps the entry it recorded under the old `git+` source and never updates it, so once `main` moves past that commit it reports `vgshell-git` as a devel update on every check, until `vgshell-git` is removed. `vgshell self status` reads `main` through `git ls-remote` ([distribution-methods.md](distribution-methods.md)). Its `pkgver()` runs the checkout's own `bin/vgshell version` and refuses any output that is not `vgshell X.Y.Z.r<N>.g<hash>`, so the package version and `vgshell --version` in that checkout agree ([distribution.md § Version](distribution.md#version)). It has `makedepends=('git')`.
- Neither recipe has `conflicts`, `replaces` or `provides`, and `scripts/check-packaging.js` refuses any such entry. The two packages own the same files, so pacman refuses to install one beside the other until the user removes the installed one.
- `install=<pkgname>.install` names the scriptlet beside the `PKGBUILD`, because an AUR repository takes no subdirectory and no file from outside it. The two scriptlets are the same text. Their `post_install` prints the [first-install text](distribution.md#first-install-text) from `/usr/share/vgshell/bin/lib/post-install.txt`. They have no `post_upgrade`.
- `scripts/check-packaging.js` holds both recipes to the requirements and to the rules above: [distribution.md § Recipe check](distribution.md#recipe-check).
- `scripts/publish-aur.sh vgshell vgshell-git` pushes both recipes to the AUR, `vgshell` only once the release asset has the sha256 the recipe pins. [RELEASING.md](../RELEASING.md) holds the release flow.
- `scripts/arch-packages.sh` builds both recipes and installs them in a rootless podman container from `archlinux:latest`, in the `package` area. Official dependencies install through the container's pacman. AUR dependencies build as its unprivileged builder. The container's root installs the results, so dependency builds ask for no authentication. Real `vgshell doctor` must report every shipped required command present after each package install. It builds the working tree as `git add -A` would commit it, and packs that commit's tarball with the release's builder ([distribution.md § Release tarball](distribution.md#release-tarball)). It installs `vgshell` with `pacman -U`, removes it with `pacman -R` and asserts it is gone, then installs `vgshell-git` with `pacman -U`. It asserts that `vgshell --version` prints `vgshell <VERSION>`, that `/usr/bin/vgshell` links to `../share/vgshell/bin/vgshell`, that pacman's output for each of `vgshell` and `vgshell-git` holds every line of the first-install text, that the `vgshell-git` pkgver carries the built commit's hash, and that its build made a partial clone. Its `prepare()` clones `file://` of a scratch bare repository that holds the built commit as `main` and serves partial clones. For each package it also asserts that the writer is a regular file `root:root 0755`, that the rule is `root:root 0440`, grants every user, sudoers' `ALL`, the writer with six hex classes and passes `visudo -cf`, and that `vgshell theme setup` reads the chromium setup `not-detected` with no browser and `done` with a stand-in `chromium` on `PATH` for the container's `builder` user, who is in no admin group. The container installs `sudo` before the packages, so `visudo` is there. Exit 77 names podman missing, a failed image pull or container start, or a failed system update or dependency download. Its header holds the keyed lines.
- On 2026-10-04 a clean `vgshell-git` build at `0.1.0.r1171.g3ee4375`, `makepkg --nodeps --nobuild` in `archlinux:latest` with git 2.56.0 and makepkg 7.1.0, received 1,159,653,279 bytes through the `git+` source, whose mirror held 399 refs, 369 of them under `refs/pull/`, and 11,245,437 bytes through the `prepare()` clone. Bytes received is the container's network interface counter around the command. A `--single-branch` clone of `main` without the filter received 24,132,156 bytes. Both recipes built the same `pkgver`, and pacman reports each package as 6.80 MiB installed. The package file is 3,187,534 bytes from the `prepare()` recipe and 3,187,562 bytes from the `git+` recipe.
- Omarchy keeps its PKGBUILDs in the separate `omarchy-pkgs` repository and serves them from its own pacman repository. Its `omarchy dev pkg-test` builds a package from a local checkout with `pkgver()` removed and installs it on the host. VGS keeps both recipes beside the source, publishes them to the AUR and runs no repository of its own. It tests in a throwaway container, so no test changes the host's packages.
