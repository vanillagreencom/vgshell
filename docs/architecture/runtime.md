## Process

- One shell per session. `bin/vgshell run` takes no arguments, takes `flock` on `$XDG_RUNTIME_DIR/vgshell.lock`, starts the shell as its child and stays in the foreground to supervise it ([D053](../decisions/D053-runner-holds-the-instance-lock.md), [D069](../decisions/D069-runner-supervises-the-shell.md)). The child writes its own pid as the lock file's only line, exports that pid as `VGSHELL_RUNNER_PID`, which every process the shell starts inherits but the programs it opens for the user ([packages.md § Running a plan](packages.md#running-a-plan)), closes its copy of the lock's descriptor and execs `qs` through `setpriv --pdeathsig TERM` with Quickshell's file watcher and reload popup disabled and `QS_PIPEWIRE_IMMEDIATE_RECONNECT` set, so a PipeWire that starts after the shell is connected once its socket appears ([runtime-devices.md](runtime-devices.md)). So the lock file and `VGSHELL_RUNNER_PID` name the shell's pid, and `vgshell pid` prints it. The runner alone holds the lock and exits after its last shell with that shell's status, so no process the shell starts holds the lock, and the lock frees when the runner exits. HUP, INT or TERM to the runner reaches the shell as TERM, and a runner killed with SIGKILL takes the shell with it. A runner that execs `qs` with the descriptor open hands the lock to every process the shell starts: on host cachy on 2026-09-29, a `/proc/<pid>/fd` scan during two nested smokes found children of the sandbox `qs`, such as `bash .../slow-download theme wallpapers --json nord`, holding the sandbox's `vgshell.lock`, and a restart or a run after a crash waited on them. `shell.qml` draws, and accepts a state-changing IPC call, only when its own pid equals `VGSHELL_RUNNER_PID`; an unguarded instance answers read-only calls and refuses the rest with `refused: guard=unowned`. Before each start of the shell, the runner creates the configuration and the state directories, whose files the shell watches from its start ([runtime-qml.md](runtime-qml.md)), and removes the plugin source snapshot roots earlier shells left under `$XDG_RUNTIME_DIR`. Quickshell 0.3.1 carries the session lock across a reload: `WlSessionLock::onReload` adopts the old lock manager, then `realizeLockTarget` calls `unlock()` when the new engine's `locked` is false (`src/wayland/session_lock.cpp`). VGS starts `SessionLock.lockRequested` false, so a file-watcher reload while locked can unlock the session. Core QML edits need `vgshell restart`: it refuses while locked with exit 4, and sends TERM to the runner, the parent of the shell's pid from the lock file when that parent holds the lock on descriptor 9, so the runner stops the shell and starts none again; a parent that holds no lock, as a runner from before D053 that execed `qs` in place, leaves TERM to the shell's pid itself. It waits up to 10 s for the instance lock, which frees when the runner exits after the shell, relaunches through `hyprctl dispatch` in the session's dialect so the shell keeps the session environment, and prints the new pid once the new shell answers as the guarded instance. Once the new run has written the lock file and the lock is free again, that run ended with no guarded shell, and restart refuses `start=exited pid=<pid|none>` at once, the pid the last one the file named; it probes the lock only after that write, when the new runner has taken it for good, so the probe never makes that runner refuse with 75. Every `vgshell` command that contacts the shell reads the pid from the lock file and addresses that instance alone; no pid, a dead pid or a failed call exits 69. `vgshell plugin validate`, `add`, `update` and `remove` work with no shell running; `add`, `update` and `remove` then end with `shell=not-running`. `vgshell theme list`, `apply`, `reload`, `add`, `update` and `remove` never contact the shell; their lock is [themes.md § Runner](themes.md#runner). A second `vgshell run` exits 75; an argument to `run` or `restart` exits 2.
- The runner supervises the shell ([D069](../decisions/D069-runner-supervises-the-shell.md)). After the shell exits it decides in this order: after HUP, INT or TERM it exits with the shell's status; after status 0, a deliberate stop, it exits 0; when `hyprctl -j monitors` gives no answer in three tries 0.5 s apart, Hyprland is gone or going, and it exits with the shell's status after `vgshell: shell=exited status=<n> hyprland=gone`. The lock file is empty from the shell's exit on, so it never names a dead pid. Otherwise it counts the exit in a streak, which a run of 60 s or more starts again, prints `vgshell: shell=exited status=<n> relaunch=<k> delay=<s> session=<locked|unlocked|unknown>` and starts the shell again after 0.5, 1, 2, 4 and 8 s. A stop signal during that wait, or during the session read, ends the runner at once, with no give-up and no relaunch line. The sixth exit of a streak gives up: `vgshell: shell=gave-up exits=<n> status=<n>`, a `hyprctl notify` error notice for 10 minutes in plain words, and an exit with the shell's status. It never gives up while `shell/Commons/SessionLockState.js`, the core's one reading of the session lock, reads the monitors as other than `unlocked`, a read that cannot run included: it starts the shell again every 8 s, since a dead shell's lock leaves only Hyprland's own screen, which a new lock client or a TTY clears ([lock-polkit.md](lock-polkit.md)). The numbers are the supervision table of `bin/vgshell`. Quickshell 0.3.1, revision 41651d7 built with its crash handler, catches SIGSEGV, SIGABRT, SIGFPE, SIGILL, SIGBUS and SIGTRAP and execs itself again in the same pid (`src/crash/handler.cpp`), so the lock file and `VGSHELL_RUNNER_PID` still name it and the runner sees nothing; a crashed instance that ran under 10 s exits -1, status 255, with `Quickshell crashed within 10 seconds of launching. Not restarting to avoid a crash loop.` (`checkCrashRelaunch` in `src/launch/main.cpp`). The runner's wait therefore meets that exit, SIGKILL, TERM and Qt's `_exit` when the Wayland connection fails, which raises no signal (Omarchy's `bin/omarchy-launch-shell` at `8b4eae6`).
- Once `vgshell run` holds the instance lock, and before its first start of the shell, it runs the pending one-time migrations with `bin/vgshell-migrate run --notice` and starts the shell whatever they answer; a failed one prints `vgshell: migrate=failed status=<n>` and runs again at the next start: [migrations.md](migrations.md), [D076](../decisions/D076-one-time-migrations.md).
- `vgshell run`, and `vgshell restart` before it stops the shell, first check the floor in the `preflight_floor` table of `bin/vgshell`: Quickshell 0.3.1, a running Hyprland 0.56, node 18, and python3 and git present. Below it they exit 78 with `vgshell: refused: preflight=<tool> have=<version|none|unknown> need=<version|present>`. The probes run at once, and the refusal names the first failing row in table order. `run` refuses before the lock, the directories and the snapshot roots. Every package recipe carries these floors as dependency constraints, and `scripts/check-packaging.js` fails until a bumped floor reaches the recipes ([distribution-arch.md](distribution-arch.md)). Outside Hyprland the check refuses ([D001](../decisions/D001-hyprland-only.md)); the smoke harness hands the shell the nested Hyprland, so it needs no skip. Node, python3 and git are hard runtime dependencies: [D009](../decisions/D009-one-manifest-judge-under-node.md#revisit-outcome-2026-09-28) § Revisit Outcome (2026-09-28). Autostart is `hl.on("hyprland.start", function () hl.exec_cmd("vgshell run") end)` in `hyprland.lua`; a system package also ships an XDG autostart entry that a uwsm session starts ([distribution-autostart.md](distribution-autostart.md)), and VGS ships no systemd unit of its own. The shell asks before it adds the line that loads the Hyprland layer, and `vgshell hypr unwire` removes it: [hyprland.md](hyprland.md). The README's autostart line must equal this one: [install-guide.md](install-guide.md).
- Quickshell 0.3.1's `qs ipc call` exits 0 for client-side IPC failures and prints the failure on stdout, including `ERROR quickshell.ipc` lines and argument errors. `bin/vgshell` and the smoke harness classify those lines through `bin/lib/ipc-reply.sh`. Its `vgs_ipc_last_line_into` gives them and `bin/vgshell-lock` the reply, the last stdout line, after one scan of a one-line reply. Bash's `${out##*$'\n'}` took 0.19 s for a 32 KiB reply and 12.2 s for a 256 KiB one (bash 5.3.20, host cachy, 2026-10-04); `scripts/test-ipc-reply.sh` bounds the reader's time. `vgshell ipc` and every other `vgshell` command that calls the shell exit 69 with `vgshell: refused: ipc=<target>.<function> reason=<key>` when the judge finds one, and an empty reply to a command that needs one exits 69 with `reason=empty-reply`. `vgshell restart` is the exception: it reads `shell.locked` and `shell.guarded` itself, refuses any `locked` reply but `true` or `false` as `locked=<reply>` with exit 1, and polls `guarded` until its bound. Its server can close before a large reply drains: `src/ipc/ipc.cpp` calls `deleteLater()` after writing the reply, so a reply past the socket send buffer, 212992 bytes (`net.core.wmem_default`), races the client's read, and a cut read prints `ERROR quickshell.ipc: Error occurred while waiting for response.` with exit 0. A reply crosses the socket at two bytes a UTF-16 character, whatever its UTF-8 length, so one of up to 106496 characters fits the buffer whole. A throwaway row of `scripts/qml-smoke.sh` on host cachy on 2026-10-04, Quickshell 0.3.1 revision 41651d7 at load 8.6, called a second qs in the nested sandbox whose handler answered N characters through `qs ipc call`, and read every reply up to 110000 characters whole: three reads of each size from 32768 in ASCII and in 2, 3 and 4 byte UTF-8, and twenty each of 106000, 106400, 107000 and 110000 ASCII characters. It cut 131072 characters in 4 of 12, 1 of 20 and 7 of 20 reads, ASCII among them, though 131072 ASCII characters are 131072 UTF-8 bytes, 200000 in 9 of 10 and 400000 in 5 of 5; a probe on 2026-09-30 cut 110000. So 32768 characters, the bound of `shell/Core/IpcPages.qml`, is a budget a third of the buffer, not the transport's limit. `listPlugins`, which grows with every plugin, and the smoke probe's replies answer through that pager: a reply past the bound answers `paged=<id>`, and the read-only `shell page <id> <index>`, which an unguarded instance answers too, hands out its pages as `<pages> <slice>`, `absent` for a reply past the eight newest. `bin/lib/ipc-reply.sh` holds the one paged-reply detector and the one page loop: every `vgshell` command that calls the shell reads a paged `shell` reply back whole and exits 69 on a bad page, as `vgshell: refused: ipc=shell.<function> reason=page-<reason> page=<index>` for a page it read, and as `vgshell: refused: ipc=shell.page reason=<key>`, such as `client-error`, for a page read that is itself cut. `vgshell ipc` passes the raw reply on, so `vgshell ipc call shell listPlugins` prints `paged=<id>` past the bound, and `vgshell plugin list` is the whole list. The smoke harness reads `shell` and `smoke` pages through the same loop and treats client failure text as a failed read.
- `qs ipc call` strips the brackets of an argument that starts with `[`, so a JSON list sent as one argument arrives as its first element's text. A caller sends a list inside an object. Read in the nested sandbox on host cachy on 2026-10-01: a list argument reached a fixture's handler as `{"output": ...}`.
- `bin/vgshell` holds the theme lock on descriptor 9 for the judge it execs, and `bin/vgshell-theme-judge`'s `LOCK_FD` names the same number. A child node spawns keeps a descriptor above 2 that the parent holds open without close-on-exec, and a spawn's `ignore` slot above 2 leaves it so: node 26.10.0 passed descriptor 300 to a child under both. Node marks its inherited descriptors 0 to 16 close-on-exec at startup (strace of node 26.10.0 on this host, 2026-09-27), which covers 9 on that build. The judge binds its own `/dev/null` descriptor to slot 9 of every reload hook, so no hook holds the lock on any build.
- Never kill Quickshell processes by name. Other Quickshell applications share the seat.
- A floating TUI needs `xdg-terminal-exec`, a default terminal whose desktop entry maps `--app-id`, `gum`, `setsid` and `script`: [tui.md § The window](tui.md#the-window).
- Never start a second shell against the live session for a test. Validation runs inside the nested sandbox.
- `Qt.quit()` and `Qt.exit()` do nothing while the root is still loading, its `Component.onCompleted` included: the log records `Signal QQmlEngine::quit() emitted, but no receivers connected`. Quickshell connects them once the root has loaded (`EngineGeneration::onReload` in [`generation.cpp`](https://git.outfoxxed.me/quickshell/quickshell/src/commit/41651d7/src/core/generation.cpp), which [`rootwrapper.cpp`](https://git.outfoxxed.me/quickshell/quickshell/src/commit/41651d7/src/core/rootwrapper.cpp) calls after `completeCreate`), so a call from a later event, such as a `Process` exit, ends `qs` with its code; the greeter host refuses that way ([greeter.md](greeter.md)). A shell exit goes through the runner.
- `qs` buffers stdout when it is redirected, so a log captured by redirection stops after the first lines. The record is the per-instance file `$XDG_RUNTIME_DIR/quickshell/by-id/<id>/log.log`, line-flushed, found through `qs list -p <checkout>/shell -j`. `console.error` lands there as `ERROR qml:` and a QML exception as `WARN scene:`.

## Performance

- One owner per watcher, poller and subprocess. Two components polling one source is a defect.
- A lookup that costs a process runs once per set, never once per item. `bin/vgshell-scan` reads every manifest and probes every declared command in one process, and the registry replaces its map whole.
- No disk walk per keystroke. A search keeps one long-lived index and cancels a stale query.
- No unconditional sleep on an apply path. Read the current value and skip the write and the wait when nothing changes.
- The first bar comes before every service. Bars, their widgets and backgrounds build in the turn the first scan ends. `ServiceHost` builds no service until `shell/Core/ServiceGate.qml` releases the services: once every bar built for that scan has presented its first frame, at once when that scan built no shown bar, as when the bar's `shown` is false, and at a 358 ms deadline otherwise, which logs a warning naming each bar host that did not present. The release logs `plugins: services released reason=<first-frame|no-bar|deadline> waited_ms=<ms>`. It happens once per shell process, so a later enable, rescan, screen change or bar rebuild builds services at once. At start a surface plugin therefore claims an exclusive capability before any service, and the theme follow on `scanFinished` never waits for the release: [D047](../decisions/D047-services-build-after-the-first-bar-frame.md).
