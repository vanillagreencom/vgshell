# Bar placement

Covers: scripts/smoke/rows/placement.sh, scripts/smoke/rows/widget-hide.sh, shell/Ui/BarWidget.qml

Whether a plugin's bar widget is in the bar. A widget shows when its plugin is installed or first discovered, and its right-click Hide takes it out. A placement edit never writes `disabledPlugins`; enablement follows from placement only for a plugin whose only kind is `bar-widget`. The Settings page's Show in bar switch ([settings-window.md](settings-window.md)) and the IPC set it; enablement is [manager.md](manager.md).

## Mechanism

- `PluginLogic.isPlaced` is the one placed reading: the manifest declares `bar-widget` and a bar section holds an entry with the plugin's id. A disabled plugin's entry still reads placed. `listPlugins` and the manager rows carry it as `placed`.
- `Plugins.setPlaced(id, placed)` is the placement operation. The IPC `setPluginPlaced <id> <true|false>` and the `manager` capability's `setPlaced(id, placed)` call it.
- `Plugins.moveWidget(id, section, index, from)` is the order operation. The IPC `movePluginWidget <id> <section> <index>` and the `manager` capability's `moveWidget(id, section, index)` move the widget's first layout entry. A drag from `BarWidget` hands `from`, the widget's own `{ section, nth }` locator, so duplicate entries keep their settings.
- `setPlaced(id, true)` places the widget at the end of its default section, `center` when the manifest names none. Enabling an unplaced widget places it through the same `PluginLogic` rule.
- `setPlaced(id, false)` removes every layout entry with the id from every section.
- Neither reads or writes `disabledPlugins`. A plugin with a kind besides `bar` and `bar-widget` stays enabled, so its service and other kinds stay built.
- A call that finds the widget as asked changes nothing. `PluginLogic.withPlaced` decides the edit. It seeds the user `bar` from the effective bar first, as every bar edit does, since a user `bar` replaces the shipped one whole ([configuration.md](configuration.md)).
- A move keeps the layout entry and its settings. The target section is `left`, `center` or `right`. The target index counts that section's entries after the moved entry is removed, and clamps to the section's end.
- The drag target is the third of the bar under the pointer, so an empty section accepts a drop. `PluginLogic.barDropTarget` returns the section, the widget the marker sits before, and the marker position. `PluginLogic.barDropIndex` maps that target to the configuration index.
- Escape cancels a drag through the KeyCapture pass-through submap, so the bar does not change its layer-shell keyboard focus during a held pointer press.
- A placed entry starts with the settings of the plugin's `plugins[]` row. The manager writes a plugin-wide setting to both entries, so a setting outlives Show in bar off and on.
- Unplacing a plugin that has no `plugins[]` row lists it there, seeded with the first removed entry's settings. The row is the record of the user's choice that the first presence reads. A third-party or `optIn` plugin of a kind other than `bar` and `bar-widget` was enabled by its placement ([plugins.md](plugins.md)), so the row keeps it enabled.
- `PluginLogic.firstPresence` names each plugin that declares `bar-widget`, sets no `optIn`, is not in `disabledPlugins`, is placed in no section and has no `plugins[]` row; `withFirstPresence` places each one in its default section. `Plugins` writes that edit after a scan that changed the plugin set and when the configuration turns ready, so a bundled or installed plugin's widget shows with no step in Settings, and a hidden one stays hidden across restarts and updates. An `optIn` plugin is placed by Enable.
- `BarWidget`, the frame every widget extends, opens a menu with one entry, Hide, on a right click. Hide asks first in a `Dialog` under the widget: it names the plugin, says the widget comes back through Show in bar on the plugin's Settings page, or through Enabled when hiding also turns the plugin off, and shows the keys in effect of its shortcuts. Cancel holds the focus. Hide calls `setPlaced(id, false)` through the `frame` the core assigns the widget.
- A plugin whose only kind is `bar-widget` has nothing left once unplaced: it reads as disabled, and Enable places it again. The IPC and the capability allow it; the Settings page draws no Show in bar for such a plugin, whose Enabled switch is its placement.
- `PluginLogic.enablementRule` names what enables a plugin: `bar`, `widget`, `first-party` or `row`. `isEnabled` matches on it, and `withEnabled` and `withPlaced` ask it whether a plugin needs a `plugins[]` row.
- The placement answers are `ok`, `unknown: <id>`, `refused: placed=<id> reason=no-bar-widget` for a plugin without that kind, `refused: placed=<id> reason=disabled` for a disabled plugin, or the user file's write refusal. `PluginLogic.placedRefusal` decides the refusal; a disabled plugin is refused as its setting is. The capability answers `refused: placed=<value> want=boolean` for a non-boolean.
- The move answers are `ok`, `unknown: <id>`, `refused: moved=<id> reason=no-bar-widget`, `refused: moved=<id> reason=disabled`, `refused: moved=<id> reason=unplaced`, `refused: section=<value> want=left|center|right`, `refused: index=<value> want=integer>=0`, or the user file's write refusal. The capability answers `refused: section=<value> want=string` before it calls the core when the section is not a string.

## Omarchy

Omarchy's `PluginRegistry.setEnabled` (basecamp/omarchy `8b4eae6`, `shell/services/PluginRegistry.qml`) drops a widget's layout entry and keeps a first-party plugin's other kinds loaded. Its disable of a first-party widget is an unplace, and the entry's settings go with the entry. VGS keeps enablement and placement as two operations, so a plugin's service and other kinds outlive its widget, and its settings outlive its entry.

## Invariants

1. A place, an unplace, a move, a repeated call and each refusal give the user file the rule above states, and no call writes `disabledPlugins`. Enforced by `scripts/test-plugin-logic.js`, with a judge copy per rule as control, among them one whose `withPlaced` writes `disabledPlugins`, one whose `withMoved` ignores the requested index and one whose drop target ignores the bar zone.
2. After `setPluginPlaced` false, true and false, and after `movePluginWidget` within a section and across sections, the bar's build records, the user `shell.json` and `listPlugins` follow each call, the plugin stays enabled, its service stays built and `disabledPlugins` is unchanged. Each refusal leaves the file as it was. A restart keeps the moved order. A pointer drag moves the same layout entry, Escape and a release outside the bar write nothing, a still click stays a click and right-click Hide still opens. Two clicks on the drawn Show in bar switch place and unplace the widget the same way, and a widget-only fixture's page draws no such switch. Enforced by `scripts/smoke/rows/placement.sh`.
3. An installed widget is placed and enabled with no further step; a right click, Hide and Cancel or Escape change nothing; Hide removes it from every bar and the user file's layout, keeps it enabled and leaves a `plugins[]` row; a restart keeps it hidden while it places a widget installed meanwhile; Show in bar brings it back. Enforced by `scripts/smoke/rows/widget-hide.sh`, whose control is a tree with no first presence and no menu, and by `scripts/test-plugin-logic.js` for each `firstPresence` rule.
