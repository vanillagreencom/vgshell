# Requirement notice

Covers: shell/Core/Notices.qml, shell/Hosts/NoticeHost.qml, shell/Core/Registry.qml, config/shell.json, shell/Core/Capabilities.qml, shell/Core/HyprlandLayer.qml, scripts/test-notice-logic.js, scripts/smoke/rows/notices.sh, scripts/smoke/rows/notices-control.sh, scripts/smoke/rows/hyprland-consent.sh, scripts/smoke/rows/hyprland-consent-decline.sh, scripts/smoke/rows/reset.sh, scripts/smoke/fixtures/plugins/acme.needs/**

The core notice host is the centred dialog surface for requirement notices, the Hyprland consent question and the first-start welcome. It is core, so it works with any set of plugins. `shell/Core/Notices.qml` holds the requirement queue, the install and the one consent slot; `shell/Hosts/NoticeHost.qml` draws one dialog at a time, requirement notice first. The same pair holds and draws the restart notice, after the requirement notices and before the consent slot: [plugins.md § What the core builds and hands over](plugins.md#what-the-core-builds-and-hands-over). After the restart notice and before the consent slot come the reset question and the "VGS was reset" notice, so the welcome follows a reset.

- **Triggers.** Six things raise a requirement notice. `pluginInstalled <id>`, the shell IPC function `vgshell plugin add` calls, starts a rescan, answers as `rescanPlugins` does, `ok scan=<N>` or `busy scan=<N>` ([plugins.md](plugins.md)), and raises the notice once the scan revision reaches N, the end of a scan started after the call. `setPluginEnabled`, and the `manager` capability's `setEnabled` through it, raises it when a plugin is turned on. The plugin's own `requirements` capability raises it through `shell.requirements.offer(commands)`. The `manager` capability's `installRequirements(id)`, the Settings window's Install all missing ([settings-window.md](settings-window.md)), raises it for any plugin, and its `act(id, key)`, and the `status` capability's `act(key)` through it for the calling plugin, raises it, through `Notices.chosen` as the `doctor` capability does, after a scan, for the commands a status action that installs names while the plugin's value offers it, a user's press no rest refuses ([status.md](status.md)). The `requirements` capability's `shell.requirements.missing` reads, and raises nothing: the plugin's declared commands the last scan did not find, in declaration order, bindable, so a plugin shows a command's presence from the scan's probe instead of probing again. `shell.requirements.revision` rises after every ended scan, result or failure, so a plugin can re-read setup state that depends on PATH. The `doctor` capability raises it for another owner through `shell.doctor.offer(owner, commands)`, below.
- **Owners.** A notice belongs to one owner: a plugin, or the core, whose owner id is `core` and whose requirements are `config/requirements.json`, drawn under the name VGS. The scan probes the core's list with the plugins' (`bin/vgshell-scan --core`), and `Registry.requirementOwners` and `Registry.ownerMissing` hold every owner's requirements and missing commands.
- **The doctor capability.** `shell.doctor.offer(owner, commands)` asks, on a user's press, for the notice of the core or of an enabled plugin, for 1 to 16 commands that owner declares. `PluginLogic.noticeOwnerError` refuses `refused: owner=malformed`, `refused: owner=<owner> reason=unknown` and `refused: owner=<id> reason=disabled`, then the offer's own refusals apply, at once. Otherwise it answers `ok`, starts a scan and raises the notice after it, listing each command that scan finds missing: the view that asks read PATH later than the last scan, as after a removal through mise, which rescans nothing. A choice is the user's act, so no rest refuses it. `shell.doctor.missing` is the last scan's missing commands of the core and of every enabled plugin, by owner id, each read a copy; a binding on it follows each scan, enable and disable. The Dev Tools window's VGS section is its consumer.
- **What each asks for.** The install and enable triggers list every missing command and keep the notice open while a command the plugin does not mark optional is missing. A plugin missing only optional commands raises none. A request from the manager lists and keeps open every missing command, optional or not, since the user asked to install them; a plugin missing nothing answers `refused: requirements=<id> reason=satisfied`. An offer lists and keeps open each of its commands still missing, optional or not. It names 1 to 16 commands, each declared in the plugin's own manifest, so a plugin never offers a package it did not declare. It answers `ok`, `satisfied` when none is missing, `refused: requirements=malformed` for anything but a list of 1 to 16 strings, or `refused: requirement=<command> reason=undeclared`.
- **Queue.** One notice per owner: a trigger for an owner that holds one merges its commands into it and answers `ok`. At most 8 plugins hold a notice. The first shows and the rest wait, and a ninth answers `refused: notices=full limit=8`. Not now, Escape and Close drop the shown notice and rest the plugin's own offers for 10 minutes: an offer then answers `refused: requirements=<id> reason=resting retry-ms=<ms>`. The install and enable triggers are the user's own acts, so no rest refuses them. The ceilings are core policy, like the toast stack's.
- **Surface.** One `OverlaySurface` in namespace `vgs:notice` ([capabilities.md](capabilities.md)), on the monitor that was focused when the notice came to the front, taking the keyboard on demand. It fills the area other layers leave free, less `dialog.margin` on every edge, and the dialog sits in its centre. Only the dialog takes pointer input, so the bar and the layers below keep their clicks. Omarchy's notification popups (basecamp/omarchy `8b4eae6`, `shell/plugins/notifications/Service.qml`) use one full-screen overlay window with a mask on the popups too, but ignore reserved space and compute the bar's clearance themselves. VGS lets the compositor subtract reserved space instead, which holds for any layer that reserves space, on any edge. It exists only while a notice shows and its install does not run, so the floating TUI the install opens on the same monitor shows whole; a notice the install leaves open maps again as a new window that takes the keyboard. The `Dialog` component draws it ([components.md](components.md)).
- **Hyprland consent.** `HyprlandLayer.qml` owns the consent question. The notice host draws the consent slot only when no requirement notice shows. The question offers Connect and Not now, and its command disclosure holds `vgshell hypr wire`. Connect answers the owner to run the wire and reload sequence. Not now and Escape answer decline. [hyprland.md](hyprland.md) gives the state machine and marker.
- **Welcome.** The consent slot draws a welcome on the shell's first start for the user, until the user closes it once. `PluginLogic.consentSlotView` decides what the slot draws from the consent state, the welcome state and the keys; `PluginLogic.welcomeStep` decides when the welcome is seen; `HyprlandLayer.qml` reads and writes the marker and binds the view to `Notices.consent`. The marker is the plain file `<Paths.stateDir>/welcome-seen`, `${XDG_STATE_HOME:-~/.local/state}/vgshell/welcome-seen`: absent shows the welcome, present never does. The welcome waits until the marker is read and the consent state leaves `pending` and `unwired`, so it never shows Close alone and then turns into a question. It draws the title Welcome to VGS, one fixed line on plugins and either two lines that explain Connect and Not now while the question is asked, or the fixed line on the one `hyprland.lua` line once the consent state settled. The cited `hyprland.lua` text opens `hypr/hyprland.lua` through `shell.tui.edit(path, line)` while the file exists; the `settled` phase has no link because `hyprland.lua` is absent or the probe could not read it. Under a Quick commands header, it draws one key row per entry of the shipped `config/shell.json`'s `welcome.keys` ([configuration.md](configuration.md)) whose plugin binds that shortcut. Each row uses `KeyCaps` for the key, the key spelled for people (`SUPER+SLASH` reads `Super+/`) by `PluginLogic.keyLabel`. The core names no plugin, so the plugin ids live in that file. While the question is asked the welcome holds it, Connect and Not now, with no Show command disclosure; once the consent state settled without one (`wired`, `settled`, `declined`) it offers Close alone. Close writes the marker; Not now and Escape write it once the decline reaches `declined`, and Connect once the consent reaches `wired`. Until then the welcome stays, busy, so it never turns into the plain question. Not now also writes the decline marker as before. A failed Connect keeps the welcome open with its failure line. A later start with the marker present and an unwired `hyprland.lua` asks the plain question, with the `vgshell hypr wire` command behind Show command. The welcome shows once per user state directory, the first time the shell starts there. A marker that cannot be read shows no welcome and a write that fails shows it again at the next start; each is logged as `welcome: marker-read=failed` or `welcome: marker-write=failed`. Omarchy (`basecamp/omarchy` `quattro` at `245630786c71`) marks first-run work done with a plain file under `~/.local/state/omarchy/done/` (`bin/omarchy-done`) and welcomes with one notification; VGS uses the same kind of marker and puts the welcome in the existing consent dialog, so the first screen holds one window, not a notification beside a question. `Notices.record` carries `welcome`: the marker state, the lines, the key rows, the link and the action labels while the slot draws the welcome.
- **Managers.** `bin/vgshell-pkg detect --json` runs when the first notice arrives and again after each install. The notice waits for the first answer. A detection that fails is logged as `notices: detect=failed exit=<code> status=<status> <first stderr line>`, and the notice lists the commands without packages.
- **Rows.** Each listed requirement reads as its purpose, with a hint under it naming the command, this system's package for it and whether it is optional. No row draws a command to run: the command Install runs, `PluginLogic.noticeView`'s `commandLine`, sits only behind the dialog's `CommandDisclosure`, closed until asked, whose toggle and Copy the dialog's Tab cycle reaches, and a notice with no Install has none ([D061](../decisions/D061-no-manual-commands.md), [status.md](status.md)). `scripts/check-user-commands.py`'s `drawn-command-line` fails any drawn property bound to a `commandLine`.
- **Install.** The notice offers Install and Not now when a detected manager installs a listed package, and Close alone otherwise. Its message then names each nix package to add to the system configuration, or says the commands are installed by hand. Install opens the core TUI `core/requirements-install`, `vgshell pkg run install [--manager <id>] <package>...`, for the first group `PackageManagers.installGroups` makes: one manager per press, primary first. The notice stays at the front of the queue until one scan after the TUI's run ended, even when a scan the run's own steps asked for already finds its commands, so no waiting notice comes forward while the terminal still holds the install's key: `PluginLogic.noticeSettle` keeps it. A notice whose required commands that scan finds is closed; otherwise it stays, offers the next group, and names a run that did not end with code 0. The package manager asks for root in the terminal, never in the shell ([tui.md](tui.md)).

Omarchy (basecamp/omarchy `e332dc97`) installs a missing terminal from `omarchy-default-terminal`, which runs itself again with `--install` in its floating terminal through `omarchy-launch-floating-terminal-with-presentation`. VGS does the same for every declared requirement: the question is a shell dialog, and the install is a floating TUI that runs `vgshell pkg run`.

## Invariants

1. A notice lists only commands its owner declares, raises none for optional commands alone, merges per owner, asks for a `doctor` request's owner only when it is the core or an enabled plugin, rests a plugin's offers after Not now and never the user's triggers, holds at most 8 plugins, keeps the installing notice through a scan until its run's own, and installs through a manager that installs. Enforced by `scripts/test-notice-logic.js`, with a judge copy per rule as control.
2. `vgshell plugin add` and enabling a plugin each raise the notice in a running shell, with the Plugins window closed; it maps on the focused monitor with the keyboard, draws each requirement as its purpose and the install command only behind a closed Show command, its surface clears the bar by `dialog.margin` with the dialog in its centre, a click on a bar widget and one beside the dialog pass through while one on the dialog's title does not, Escape closes it, Install hands the terminal `vgshell pkg run install` with the primary's package, the notice has no surface while the run is live, a scan during the run keeps the installing notice in front of a waiting one, and only the scan after the run closes it. Enforced by `scripts/smoke/rows/notices.sh` in the nested sandbox, with the fixture `acme.needs`, a stand-in `bin/vgshell-pkg` for detection and `scripts/smoke/rows/tui.sh`'s stand-in terminal. The rescan row's control is the install before the command exists, which leaves the notice open. The same row reads `shell.requirements.missing` from the fixture before the install, after it and after the command goes; the reading before the install and the one after it are each other's control. `scripts/test-notice-logic.js` fails on a judge copy whose `noticeSettle` drops the installing notice. The enable trigger's control is `scripts/smoke/rows/notices-control.sh`, the suite's last row: it stops the running shell, starts a copy of the tree whose `Plugins.setEnabled` does not call `Notices.enabled` as the guarded shell, and reads no notice after enabling `acme.needs`.
3. The welcome shows while its marker is absent and never once it is present; it waits for the marker's read and for the consent answer; it asks with Connect and Not now while the question is asked and offers Close alone once the consent settled; it has no command disclosure while it asks; its cited file opens through the core edit TUI; a key row shows only while its shortcut is bound, with the bound key; Close marks it seen, a Not now or Escape that declines and a Connect that wires mark it seen when the consent moves, the welcome staying until then, and a failed Connect keeps it. Enforced by `scripts/test-notice-logic.js`, with a judge copy per rule as control, among them one that ignores the seen state and one that always draws the key row. On the nested instance the first start draws the welcome with its link, key chips and no command disclosure, fits a 1440x900 output without scrolling, whose control is a 1440x320 output it overflows, and Connect writes the marker; a later start with an unwired `hyprland.lua` draws the plain question; Escape on the welcome that asks writes both markers and keeps the welcome, busy, while the decline runs, whose control is a copy that marks it seen on the answer and shows the plain question there; a wired start without the marker draws the welcome with Close alone, Escape closes it and writes the marker, and a start with the marker draws nothing. Enforced by `scripts/smoke/rows/hyprland-consent.sh` and `scripts/smoke/rows/hyprland-consent-decline.sh`.
4. The `doctor` capability raises an enabled plugin's notice from another plugin's press after a scan, raises none for a core command that scan finds, refuses a command the core does not declare and a disabled or unknown owner, and its `missing` follows the scan. Enforced by `scripts/smoke/rows/devtools.sh` in the nested sandbox, whose control copy of the Dev Tools service ignores a change of `missing` and keeps a disabled plugin's requirement, and the owner rule by `scripts/test-notice-logic.js`.
