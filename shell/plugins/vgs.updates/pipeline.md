# Update pipeline

The plugin declares two floating TUIs that update.

- `update` runs `tui/update.sh`: every source in one run. The plugin's Packages category in the launcher opens it.
- `update-source` runs `tui/update-source.sh <source>`: one source. `<source>` is a status row's `source`: the primary package manager's id, `aur`, `flatpak`, `mise`, `vgs`, `plugins` or `themes`. It is not listed, because it needs its argument: `shell.tui.run("update-source", [source])` opens it.

Both take `-y`, which skips the start question only. They share `tui/pipeline.sh`, whose header is the full contract. A run takes these steps in this order:

1. The log and the lock. `script` writes the run to `${XDG_STATE_HOME}/vgshell/updates/update.log`. The lock is `${XDG_RUNTIME_DIR}/vgs-tui-updates.lock`. A second run exits 75 and leaves the first run's log as it is.
2. A warning when `/` has less than 10 GiB free.
3. The plan box: the snapshot tool, each source with the commands it runs, and the log path. Then `Start the update?`, unless `-y`.
4. The shared package owner prepares and retains the effective configuration and offers the review before snapshot or credentials: [§ Third-party review](#third-party-review). A missing helper is installed first as its own reviewed prerequisite transaction, whose credential session ends before this preparation.
5. One sudo session, when a snapshot or the system step needs root and the elevation command is `sudo`. `vgshell pkg run` joins it, so the password is asked once. The elevation command is the one `vgshell pkg plan upgrade <primary>` names: `packages.elevate` in `shell.json`, else the first of `sudo`, `doas` and `run0` on `PATH`. `doas` and `run0` ask as their own rules say.
6. A snapshot through snapper, else timeshift, behind the elevation command. It comes before any step that replaces a package: the system upgrade, the AUR upgrade or the `vgshell-git` rebuild. No snapshot is taken when the `snapshot` setting is `off`, when neither tool is on `PATH` or when no elevation command resolves. The plan box says which. A tool that fails or has no configuration prints a warning, and the update continues without a snapshot.
7. VGS itself: `vgshell self update` when `vgshell self status` names the step `self`, a checkout or a curl install that is behind. It restarts a running shell. A step of `none` runs nothing for VGS, and the plan box names its reason: the release `vgshell` package under pacman needs an AUR helper, any other package updates with its package manager, and a Nix tree with its flake. The release `vgshell` package with no AUR helper updates with its package manager where the `aurCommand` setting holds words, because the AUR step runs them. The `install-helper` prerequisite has already installed paru before shared review preparation.
8. The system: `vgshell pkg run upgrade --manager <primary>`.
9. Flatpak and mise: `vgshell pkg run upgrade --manager flatpak`, then `--manager mise`.
10. Each plugin, then each theme, that is behind its upstream: `vgshell plugin update <id>` and `vgshell theme update <name>`. Each shows its diff and asks `[y/N]`. The pipeline passes `--yes` only when `trustPluginUpdates` is on. A declined update reads skipped in the result list, and the run continues.
11. The end of the sudo session. The credential is dropped.
12. The AUR, last: the `aurCommand` setting's words, else `vgshell pkg run upgrade --manager aur` (`paru -Sua` or `yay -Sua`). No AUR build runs under the update's credential. When the status names `rebuild`, the table-backed `vgshell pkg run reinstall --manager aur vgshell-git` follows with its own prepared decision, because an AUR helper rebuilds a `-git` package only when its recipe's version changes. The rebuild removes `${XDG_STATE_HOME}/vgshell/updates/rebuild-failed.json` before it runs. When it fails, it writes that file again, one JSON object `{ current, helper, exit, conflict }`: the installed version it tried to replace, the helper, the helper's exit status, and the first package of pacman's `:: <a> and <b> are in conflict` line in the helper's output, without its version, or null. The helper asks `sudo` itself. The credential it caches is dropped when this step ends, fails or is interrupted.
13. On pacman, after a system or AUR upgrade, the orphaned packages from `pacman -Qtdq`, with `Remove N orphaned package(s)?`, default no. A yes runs `vgshell pkg run remove --manager pacman`.
14. A shell restart, when a package step or the `vgshell-git` rebuild replaced the VGS package.
15. The result list, `Update result`: one line per step of 7 to 10 and 12 and per package the review skipped, `<item>: installed`, `<item>: skipped, <reason>` or `<item>: failed, <cause>`.
16. A reboot question, `Reboot` or `Later`, default Later, when the run changed a package that takes effect after a reboot, or the kernel or the running Hyprland binary was replaced (`vgs_tui_reboot_check`). On pacman the run reads `pacman -Q` before its first package step and after its last. A package whose version changed, or a new one, takes effect after a reboot when CachyOS's reboot hook, `usr/share/libalpm/hooks/cachyos-reboot-required.hook` under pacman's `RootDir`, names it for that operation and the hook script's conditions hold: an NVIDIA module only for the running kernel, and a file system tool only while its file system is mounted (`UpdatesLogic.rebootPackages`). Without the hook no package does. The Reboot notice setting VGS only turns the CachyOS notice off, so this question is the only one, and the run still reads the hook. A yes runs `vgshell power reboot`, which lets a running Jarvis session save its work first.

Every package step is the package table's own plan, from `vgshell pkg plan upgrade <id>`. The steps take no `-y`, so each manager asks its own questions in the terminal. A package source without an upgrade plan, such as `nix`, is left out of the run with the reason in the plan box.

With `-y`, the orphan list and the reboot reason are printed instead of asked. The review's questions are still asked.

A failing step of 7 to 10 or 12 records its cause, else `exit <n>`, and the run goes on with every later step. The cause is read from the step's output: the last error line, one that starts pacman's `error:`, else the last line. After a VGS refusal line, `vgshell: refused:` or `vgs-tui: refused:`, it is the last line after the refusal, else the refusal's value, except after `vgshell pkg run`'s closing `rescan=` refusal, where it is the package manager's last error line before it, else its last line. The line `vgshell pkg run` prints on stdout after its steps however they ended, `shell=rescan-started`, `shell=rescan-queued` or `shell=not-running`, closes its block the same way and is never the cause or the answer. A step whose output ends on a `[Y/n]` or `[y/N]` question answered no or left unanswered, or a declined plugin or theme update, reads skipped, you declined it. After a failed or declined system step, the AUR step and the `vgshell-git` rebuild do not run and read skipped, since AUR packages build against the system that step left; every other step still runs. A run with a failed step says so after the result list and exits 1 after the reboot question. A step a Ctrl-C ends stops the run with 130. Any other failing step stops the run: the terminal shows `updates: failed exit=<n> log=<file>` and how to recover. The sudo session, or the guard around the AUR, drops the credential on the way out.

A step keeps the terminal on stdin, stdout and stderr, so both output streams reach the terminal through one pseudo-terminal in the order the step wrote them, and pacman's `[Y/n]` shows on its own line after its size summary. A stderr that is not the terminal split them: under `sudo`'s `use_pty`, on by default since sudo 1.9.14 (`sudoers(5)`), sudo relays the command's terminal output through a pseudo-terminal of its own to `/dev/tty` and hands a stream that is not the user's terminal to the command unchanged (sudo `src/exec_pty.c`), so pacman's question passed its summary. The output of a failed step is cut from the run's transcript, the unchanged copy `vgs_tui_log`'s `script(1)` keeps in the runtime directory and removes at the run's end, between two marks the run writes before and after the step: an OSC sequence no terminal handles, which the terminal does not draw and the log leaves out. When the end mark does not reach the transcript within 10 s, the cause reads that VGS could not read the step's output, and the developer log gets `updates: transcript=unread source=<id> reason=<absent|late|lost|copy-failed>`. A closed window hangs up the terminal: the step's later writes fail with EIO instead of killing it, so pacman still unlocks its database.

The TUIs read the plugin's settings with `vgshell plugin settings vgs.updates`, since `shell.tui.open` hands a script no arguments. `bin/facts` reads each `vgshell` JSON answer for the shell script. The VGS step is the status's own `step`. Whether a plugin or a theme is behind is `UpdatesLogic.js`'s decision, as for the service.

When a run ends, the service checks again ([developer.md § Cadence](developer.md#cadence)).

## Third-party review

The package owner supplies the same review for Updates and every package install. Updates prepares each source's effective hook-mask configuration before the owner's pending queries and review, retains it through execution, and passes one private request/result pair in its transaction directory. Each later upgrade or named rebuild enters common package admission with the owner's opaque receipt and consumes only its exact bound step once. The transaction removes unused authority on completion or cancellation.

Review runs in this terminal before the snapshot and Updates credential session. It uses the shared package settings and the common agent, verdict and install-script judges. A missing helper is a separate prerequisite transaction: its own offer precedes its credentials/build, its session ends, and then Updates reviews against that actual helper. A missing, stale, consumed or unreadable binding stops before mutation; no second review starts inside a credential session. [Commands are data](../../../docs/architecture/commands-are-data.md#package-review) holds the owner and consent rules.

Recognized custom AUR commands enter the table's common upgrade admission. Unsupported commands have unknown coverage and require explicit unavailable-review continuation before credentials; their original argv receives no package-skipping or clean verdict. Updates owns source ordering, snapshots, hook masking, results, orphan decisions and reboot decisions. It owns no agent detector, review settings, verdict parser, review prompt, review TUI or second-window handshake.

## Scope

Low free space is a warning, not a refusal, so a user with a small disk can still update.

The pipeline runs no migrations, keyring step, channels or ALPM guard: those are a distribution's work, and VGS is not a distribution. A run does not hold the system awake.
